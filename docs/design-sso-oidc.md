# 통합 로그인(OIDC) 연동 대비 설계 (작업 78-1)

> 상태: **설계 문서(구현 없음)**. 코드·DB·설정·프론트·테스트는 바뀌지 않았다. 표의 "사실"은 현재 저장소 코드를 읽어 확인한 내용이고, "제안"은 이 문서가 새로 정하는 내용이다.
> 연동 앱의 제품명은 쓰지 않고 "연동 앱"으로만 적는다.

## 1. 목표·비목표·용어

| 구분 | 내용 |
|---|---|
| 목표 | 사용자·부서·사용권한을 AI DOTS 한 곳에서 관리하고, 같은 고객사가 함께 쓰는 연동 앱은 AI DOTS 로그인을 그대로 사용한다(한 번 로그인) |
| 비목표 | 외부 소셜 로그인, 다른 회사 계정 연합, 연동 앱 쪽 사용자·권한 관리, 동의 화면, 이번 작업의 구현 |
| 보안 원칙 | 모든 서비스는 로컬 LLM 기반. 외부망 연동은 기본 OFF. 시스템 설정 변경은 시스템 관리자만. 권한은 서버에서 검증(앱의 자기신고 금지). 두 제품은 독립 운영하고 API 로 협력 |
| 대상 규모 | 직원 200명 이하 중소기업, 인터넷 연결 환경이 많고 폐쇄망도 있음(→ 외부 서비스 의존 없이 동작해야 함) |

| 용어 | 뜻 |
|---|---|
| Provider(OP) | 로그인을 발급하는 쪽 = AI DOTS |
| Relying Party(RP) | 로그인을 받아 쓰는 쪽 = 연동 앱 |
| 클라이언트 | Provider 에 등록된 RP 한 건(client_id) |
| 사용권한 | 현재 코드의 `accounts.rank`: staff(담당자) < manager(관리자) < executive(지시자) |

## 2. 현재 구조(사실)

| 항목 | 현재 상태 | 근거 위치 |
|---|---|---|
| 로그인 API | `POST /api/auth/login`(login_id+비밀번호) → `{access_token}`, `GET /api/auth/me` | `app/api/auth.py` |
| 토큰 | JWT **HS256**, 클레임 `sub`(계정 id)·`iat`·`exp`만. 서명 키는 설정 `SECRET_KEY`(대칭), 만료 `ACCESS_TOKEN_MINUTES`(기본 480). 알고리즘 HS256 만 허용 | `app/auth/tokens.py` |
| 보조 토큰 | 음성 재생용 서명 주소 토큰(`typ=audio`, 10분, 같은 비밀값) | `app/auth/tokens.py` |
| 비밀번호 | argon2 해시, 없는 ID 도 해시 시간을 써서 존재 여부 은닉, 실패 문구 통일 | `app/auth/passwords.py` |
| 인증 의존성 | `get_current_account`: Bearer 검증 + 계정 존재·활성 확인(아니면 401), `require_rank`(403) | `app/auth/deps.py` |
| 계정 표 | `accounts`: id, tenant_id, login_id(전체에서 유일), password_hash, name, email, rank, is_active, created_at | `app/models/account.py` |
| 조직 | `departments`(고객사별 이름 유일, 상위 부서 `parent_id`, kind=normal/executive 임원 그룹), `account_departments`(계정×부서×역할 head/member, 겸직 가능) | `app/models/org.py` |
| 부서장 규칙 | 부서마다 1명은 DB 제약이 아니라 서비스 계층에서 보장 | `app/services/org.py` |
| 고객사 | `tenants`: 모든 업무 데이터가 tenant_id 로 구분 | `app/models/tenant.py` |
| 권한 판정 | 회의록 열람·확정·총괄·대체 등은 `auth/access.py`·`auth/actions.py` 에 모여 있음(서버 판정, 허용 동작을 응답에 담아 화면은 표시만) | `app/auth/` |
| 시스템 관리자 | **개념만 있고 구현 없음**. 조직 등록·수정 API 는 "시스템 관리자 기능 때 만든다"고 주석에만 있고 지금은 `scripts/manage_org.py`. 사용권한(rank)에 시스템 관리자 값이 없음 | `app/services/org.py`, CHANGELOG |
| 토큰 저장(프론트) | `sessionStorage`(탭을 닫으면 사라짐), 키 `mi.v2.accessToken`. httpOnly 쿠키 전환 계획 문서는 저장소에서 찾지 못함 | `frontend/lib/v2/token.ts` |
| CORS | 설정 `CORS_ORIGINS`(쉼표 목록, `*` 시작 거부), 쿠키 없는 Authorization 헤더 방식이라 credentials 끔 | `app/main.py`, `app/config.py` |
| 이력 | 사건 원장 `events`(추가 전용): 대상·종류·행위자·payload. 로그인 시도·토큰 발급 기록은 없음 | `app/models/event.py` |
| 속도 제한·잠금 | 로그인 시도 제한 없음 | — |

## 3. 인증 흐름(제안)

### 3.1 기본 흐름: Authorization Code + PKCE(S256)

```
연동 앱(브라우저)                AI DOTS(Provider)
 1 /authorize?client_id&redirect_uri&code_challenge&state&nonce&scope=openid profile
                              → 로그인 화면(기존 화면 재사용, 이미 로그인했으면 건너뜀)
                              → redirect_uri?code=...&state=...
 2 연동 앱 서버: POST /token (code, code_verifier, client 인증)
                              ← id_token, access_token(짧은 수명)[, refresh_token]
 3 연동 앱: id_token 검증(서명·iss·aud·exp·nonce) → 자체 세션 생성
 4 필요 시 GET /userinfo (access_token)
```

| 엔드포인트(제안) | 역할 | 입력 → 출력 |
|---|---|---|
| `/.well-known/openid-configuration` | discovery | 없음 → issuer, 각 엔드포인트, 지원 알고리즘·스코프·클레임 |
| `/oidc/authorize` | 인가 코드 발급 | client_id, redirect_uri(정확 일치), response_type=code, scope, state, nonce, code_challenge(S256 필수) → 리다이렉트로 code·state |
| `/oidc/token` | 코드 교환·갱신 | grant_type=authorization_code(code, code_verifier, redirect_uri) 또는 refresh_token → id_token, access_token, expires_in |
| `/oidc/userinfo` | 사용자 정보 | Bearer access_token → 클레임(§4) |
| `/oidc/jwks` | 공개 키 | 없음 → JWK Set(kid 별 공개키) |
| `/oidc/logout` | 로그아웃(RP-initiated) | id_token_hint, post_logout_redirect_uri(등록된 것만), state → 세션 종료 후 리다이렉트 |

| 쓰지 않는 흐름 | 이유 |
|---|---|
| Implicit | 토큰이 URL 에 노출, 표준에서도 지양 |
| Password grant(ROPC) | 연동 앱이 비밀번호를 직접 받게 되어 단일 로그인 목적에 반함 |
| Client credentials | 사용자 로그인 목적이 아님(앱 간 job 의뢰용 API 인증은 별도 설계) |

### 3.2 화면 재사용과 동의 화면 생략
- 로그인 화면은 기존 AI DOTS 로그인 화면을 그대로 쓰고, `/authorize` 가 미로그인 상태면 로그인 후 원래 요청으로 복귀한다(제안).
- 동의 화면은 생략한다: 연동 앱은 **같은 사업자가 같은 고객사에 함께 납품하는 앱**이고, 클라이언트를 시스템 관리자가 직접 등록·승인하므로 사용자가 제3자에게 권한을 위임하는 상황이 아니다. 단, 등록되지 않은 client_id·redirect_uri 는 즉시 거부한다.

## 4. 토큰·클레임 설계(제안)

| 클레임 | 내용 | 비고 |
|---|---|---|
| `iss` / `aud` / `exp` / `iat` / `nonce` | 발급자·대상 클라이언트·만료·발급·재전송 방지 | 표준 |
| `sub` | **불변 계정 식별자**(현재 `accounts.id` 를 문자열로) | login_id 는 바뀔 수 있어 쓰지 않음. 장비 간 이관을 고려하면 별도 UUID 칸 검토(미결 질문) |
| `name` | 이름 | |
| `tenant` | 고객사 id·이름 | 연동 앱은 같은 고객사 사용자만 허용 |
| `rank` | `executive`·`manager`·`staff`(지시자·관리자·담당자) | 값은 영문 코드, 표시 이름은 앱이 정함 |
| `departments` | `[{id, name, role: head|member}]` | 겸직 반영, 상위 부서(parent_id)와 임원 그룹(`kind=executive`) 여부 포함 |
| `is_executive_group` | 임원 그룹 소속 여부 | `departments` 에서 계산 가능, 편의 필드 |
| `active` | 활성 여부 | 비활성 계정은 토큰 자체를 발급하지 않음. 값은 userinfo 확인용 |
| 제외 | 비밀번호·해시, 이메일(필요 시 `email` 스코프로만), 전화번호, 주민번호류 | 최소 정보 원칙 |

| 항목 | 제안 |
|---|---|
| 서명 | **RS256 또는 ES256(비대칭)**. RP 가 공개키(JWKS)만으로 검증해야 하므로 기존 HS256 `SECRET_KEY` 는 쓰지 않는다. 기존 로그인 토큰(HS256)은 그대로 유지 |
| 키 관리 | OIDC 서명 키쌍을 별도로 생성·보관, `kid` 부여, 회전 시 이전 공개키를 JWKS 에 유예 기간(최대 토큰 수명) 동안 함께 게시 |
| 수명 | id_token 5분(로그인 확인용), access_token 10~15분, refresh_token 8시간 이내(현행 로그인 480분과 맞춤) |
| 리프레시 | 사용할 때마다 교체(rotation), 재사용 감지 시 해당 계열 전체 폐기. 저장은 해시만 |
| 인가 코드 | 1회용, 60초, PKCE 바인딩, 사용 즉시 소모 |

## 5. 연동 앱(클라이언트) 등록·관리(제안)

| 항목 | 내용 |
|---|---|
| 관리 주체 | **시스템 관리자만**(서버에서 검증). 현재 시스템 관리자 개념이 구현되어 있지 않아 선행 필요(§8) |
| 등록 값 | client_id(공개 식별자), 이름, redirect URI 허용 목록(**정확 일치**, 와일드카드 금지), post_logout redirect 목록, 허용 스코프, 고객사 범위, 활성 여부 |
| 시크릿 | 서버 간 연동용 기밀 클라이언트는 시크릿 발급, **해시로만 저장**, 화면에는 발급 직후 1회만 표시, 재발급 시 이전 값 즉시 무효 |
| 공개 클라이언트 | 브라우저 단독 앱은 시크릿 없이 PKCE 만 사용 |
| 비활성화 | 즉시 신규 인가·갱신 거부(이미 발급된 짧은 수명 토큰은 만료까지 유효) |
| 이력 | 등록·변경·시크릿 재발급·비활성화는 사건 원장에 행위자와 함께 기록(시크릿 값은 기록 금지) |

## 6. 권한·조직 매핑 규칙(제안)

| 원칙 | 내용 |
|---|---|
| 서버 검증 | 연동 앱은 토큰의 클레임으로만 사용자·권한을 알고, **앱 화면에서 권한·부서를 직접 고르게 하지 않는다**(자기신고 금지). 앱의 서버가 id_token 서명을 검증해 사용 |
| 사용권한 대응 | `executive`→앱의 최상위 열람 등급, `manager`→중간 등급, `staff`→기본 등급. 대응표는 앱이 정하되 기준은 클레임 `rank` 하나 |
| 부서 대응 | 앱의 고정 부서 목록을 쓰지 않고 클레임 `departments` 를 사용. 앱의 문서 "허용 부서"는 부서 **id** 로 저장하고 이름은 표시용으로만 사용(이름 변경에 안전) |
| 부서장·임원 그룹 | `role=head` 를 부서장 전용 기능의 판정에 사용, 임원 그룹 소속은 임원 열람 규칙에 사용 |
| 계층 | 상위 부서 관계는 필요 시 userinfo 로 부서 트리를 조회(토큰에는 직속 소속만) |
| 변경 반영 | 부서·권한이 바뀌어도 이미 발급된 토큰에는 반영되지 않으므로 토큰 수명을 짧게 하고 갱신 시 최신 값을 다시 읽는다(§7) |

## 7. 세션·로그아웃·비활성화 전파

| 방식 | 장점 | 단점 | 제안 |
|---|---|---|---|
| 짧은 토큰 수명 + 갱신 때 재확인 | 구현 단순, 별도 통신 없음 | 비활성화 반영이 수명만큼 지연 | **1단계 기본**(access 10~15분) |
| 폐기 목록(revocation) / introspection | 즉시 반영 가능 | RP 가 매 요청 또는 주기적으로 Provider 를 호출해야 함 | 선택 도입(민감 기능만) |
| back-channel logout | 로그아웃·비활성화를 RP 서버에 즉시 통지 | RP 가 수신 엔드포인트를 제공해야 하고 네트워크 도달 필요, 폐쇄망 구성이 복잡 | 2단계 이후 선택 |
| front-channel logout | 구현 쉬움 | 브라우저 의존, 신뢰도 낮음 | 비권장 |

- 로그아웃: AI DOTS 로그아웃 시 Provider 세션과 리프레시 계열을 폐기하고, 등록된 RP 에는 `/oidc/logout` 로 이동. RP 는 자체 세션도 종료한다.
- 계정 비활성화: 토큰 발급·갱신 단계에서 `is_active` 를 항상 확인하고 비활성이면 리프레시 계열을 폐기한다. 이미 발급된 access 는 만료까지 유효하다(수명이 짧으므로 허용).

## 8. 보안 체크리스트

| 항목 | 내용 |
|---|---|
| PKCE | 모든 클라이언트에 S256 필수, plain 거부 |
| state / nonce | state 는 RP 가 검증, nonce 는 id_token 에 포함되어 RP 가 검증 |
| redirect URI | 등록 값과 **정확 일치**만 허용, 오류 시 리다이렉트하지 않고 오류 화면 |
| 토큰 저장 | AI DOTS 프론트는 현재 sessionStorage. Provider 세션(쿠키)은 httpOnly·Secure·SameSite=Lax 로 두는 것을 제안하며, 쿠키 전환은 이 설계와 함께 결정해야 함(저장소에 전환 계획 문서가 없음 → 미결 질문) |
| 전송 | HTTPS 는 앞단 리버스 프록시에서 종료하는 것을 전제로 하고 앱은 HTTP 유지. issuer·redirect URI 는 https 만 허용(개발 환경 예외 설정) |
| 속도 제한 | `/login`·`/token`·`/authorize` 에 IP·계정별 시도 제한과 일시 잠금(현재 없음) |
| 감사 이력 | 로그인 성공·실패, 코드 발급, 토큰 발급·갱신, 로그아웃, 클라이언트 변경을 사건 원장에 기록(토큰·시크릿 값 제외) |
| 시간 동기 | exp·nbf 검증을 위해 서버·연동 앱 장비의 시간 동기(NTP 등) 필요, 허용 오차 60초 내외 |
| CORS | `/token`·`/jwks` 등 서버 간 호출은 CORS 불필요, 브라우저가 직접 부르는 엔드포인트만 허용 출처에 포함 |
| 고객사 격리 | 클라이언트·키·코드 모두 tenant 범위로 구분, 다른 고객사 사용자 토큰 발급 금지 |

## 9. 현재 구조와의 격차(초안, 마이그레이션 만들지 않음)

| 항목 | 격차 | 새 표·변경 초안 |
|---|---|---|
| 서명 키 | 현재 HS256 대칭키뿐 | `oidc_signing_keys`(kid, 알고리즘, 공개키, 개인키 보관 방식, 상태 active/retired, 생성·회전 시각) |
| 클라이언트 | 없음 | `oidc_clients`(client_id, 이름, 시크릿 해시, redirect URI 목록, 스코프, tenant, 활성, 생성·변경자) |
| 인가 코드 | 없음 | `oidc_auth_codes`(코드 해시, client, 계정, code_challenge, nonce, 만료, 사용 여부) — 짧은 수명이라 정리 작업 필요 |
| 리프레시 | 없음 | `oidc_refresh_tokens`(해시, 계열 id, client, 계정, 만료, 폐기·교체 표시) |
| 계정 식별자 | `accounts.id`(정수, 장비마다 다름) | 장비 이관·복수 설치에서도 불변인 `sub` 가 필요하면 `accounts.subject_uuid` 칸 추가(필수는 아님) |
| 시스템 관리자 | 개념만 있음 | 사용권한 값 추가(`rank` 확장) 또는 별도 플래그 중 선택 필요. **`accounts.rank` 에 CHECK 제약이 있어 값 추가는 마이그레이션이 필요**하고, 기존 `require_rank`/`RANK_ORDER` 서열 판정과 충돌하지 않게 "시스템 관리자는 서열이 아닌 별도 플래그"를 제안 |
| 로그인 | 시도 제한·잠금·이력 없음 | 속도 제한 저장소(메모리 또는 표), 사건 종류 추가 |
| 이메일 | `accounts.email` 은 있으나 유일성·검증 없음 | 스코프 `email` 을 쓸 때만 필요, 우선순위 낮음 |
| 로그인 아이디 | 전체에서 유일(고객사별이 아님) | 현행 유지 가능(고객사 간 충돌 방지), 고객사별 로그인으로 바꾸면 영향 큼 |

충돌 점검: 현재 사용권한 판정(`has_rank`·허용 동작)은 `accounts.rank` 와 부서 소속 표를 서버에서 읽는 구조라 OIDC 도입으로 바뀌지 않는다. 토큰의 `rank`·`departments` 는 **연동 앱을 위한 출력**이고, AI DOTS 내부 판정은 계속 DB 를 직접 본다. 다만 부서장 규칙(부서마다 1명)이 서비스 계층 보장이므로 토큰 발급 시점의 최신 값을 읽도록 해야 한다.

## 10. 구현 방식 비교

| 구분 | 직접 구현 | 후보 라이브러리(설치 금지, 확인 필요) | 외부 인증 서버 제품 도입 |
|---|---|---|---|
| 예 | FastAPI 로 엔드포인트 작성(현재 PyJWT 사용 중) | Authlib(OIDC Provider 지원), oauthlib 계열 — **라이선스·유지 상태 확인 필요** | Keycloak, Authentik 등 별도 서버 — **라이선스·요구 사양 확인 필요** |
| 통제권·일관성 | 높음(기존 계정·부서 표 그대로) | 중간(저장소·모델 연결 코드를 직접 작성) | 낮음(사용자·조직을 동기화하거나 이전해야 함) |
| 개발 규모 | 중간~큼 | 중간 | 작음~중간(연동 설정) |
| 운영 부담 | 낮음(앱 하나) | 낮음 | **높음**(별도 서버·DB·메모리, 중소기업 단일 PC 환경에는 부담) |
| 보안 책임 | 직접(표준 준수 검증 필요) | 라이브러리가 일부 분담 | 제품이 분담하나 설정 오류 위험 |
| 폐쇄망 | 문제 없음 | 문제 없음 | 설치·업데이트 절차 필요 |
| 제안 | 규모가 작고 계정·부서 표가 이미 있으므로 **라이브러리 도움을 받은 직접 구현**을 기본 후보로 제안, 도입 전 라이선스 확인 | | 고객이 이미 인증 서버를 쓰는 경우에만 RP 로 연동(선택) |

## 12. 미결 질문(결정 필요)

1. **시스템 관리자 모델**: 사용권한(rank)에 값을 더할지, 서열과 무관한 별도 플래그로 둘지(권장: 별도 플래그).
2. **계정 식별자(sub)**: 현재 정수 id 를 그대로 쓸지, 이관·복수 설치를 위해 불변 UUID 칸을 추가할지.
3. **서명 알고리즘**: RS256(호환성 높음) 과 ES256(키 작음) 중 연동 앱이 지원하는 쪽.
4. **구현 방식**: 라이브러리 도움을 받은 직접 구현으로 갈지, 고객 환경에 따라 외부 인증 서버 연동(RP 모드)도 허용할지.
5. **토큰 저장 방식**: 프론트의 sessionStorage 를 httpOnly 쿠키로 전환하는 시점(OIDC 와 같이 할지 따로 할지).
6. **비활성화 반영 속도**: 짧은 토큰 수명만으로 충분한지, 즉시 반영(폐기 목록·back-channel)이 필요한 기능이 있는지.
7. **이메일 사용**: 연동 앱이 이메일을 필요로 하는지(필요 시 스코프로만 제공, 유일성 정책 필요).
8. **연동 앱의 개조 범위**: 연동 앱이 현재 자체 인증이 없다면 권한·부서 판정을 토큰 기반으로 바꾸는 작업을 누가 어느 단계에서 할지.
