## 1) 전제와 범위

### 1.1 전제
- **[확정]** 제품 정체성은 임원을 위한 실행 관리 어시스턴트이며, 핵심 회의와 해야 할 일의 체크·리마인드·점검·최종 실적을 다룬다(부록 A-1).

## 3) 상태 모델

### 3.1 상태를 나누는 축
- **[제안]** 서로 다른 세 축을 한 열에 섞지 않는다.
  1. **처리 작업 상태**(현재 `jobs.status`): 음성 → 전사 → 추출 파이프라인의 진행.
  2. **회의록 상태**: 회의록 문서의 생애(작성 중 → 확인 중 → 확정 …).
  3. **항목 확정 상태 / 항목 진행 상태**: 항목별 확정 여부와, 확정 뒤 실행(진행·완료·종결) 여부.
- 현재는 처리 작업 상태(`queued/processing/completed/failed`, `app/schemas/models.py` `AdminJob.status`)와 액션아이템 진행 상태(`open/in_progress/done/overdue`, `app/schemas/models.py` `ActionItem.status`)만 있고, 회의록 상태·확정 상태는 없다.

### 3.2 처리 작업 상태(무음 상태 추가)
- **[확정]** 무음·전사가 빈 파일은 failed도 completed도 아닌 별도 상태 "내용 없음, 파일 확인 요청"으로 한다. 전사는 정상인데 액션아이템이 0건이면 이 상태가 아니라 정상 완료다. v2 첫 과제로 이관한다(부록 A 추가 결정).
- **[제안]** 코드 값 `no_content`, 화면 라벨 "내용 없음, 파일 확인 요청". 상태 점 색은 회색 계열(Mono Dark 규칙상 유채색은 Blue/Teal/Red만 쓰므로), 반드시 글자 라벨과 함께 표시.
- 현재 코드와 문서의 차이(확인함):
  - 코드: 전사가 비었거나 정확히 `[NO_SPEECH]`이면 `failed` + 사유 "말소리가 감지되지 않았습니다…" (`app/pipeline/service.py` 451~453행, 테스트 `tests/test_pipeline.py` `test_no_speech_fails_job_with_reason_and_keeps_file`).
  - `CHANGELOG.md` v1.10.0 "알려진 제한사항": 실제 무음 파일은 `completed`·0건으로 끝났다고 기록. 이 차이의 원인(예: Gemini가 `[NO_SPEECH]` 대신 다른 글자를 돌려준 경우)은 **확인 못 함**.
  - **[제안]** 판정 기준은 "모델이 정확히 `[NO_SPEECH]`를 돌려줬는가"에만 기대지 말고, 전사 줄 형식(`[HH:MM:SS] 화자: 내용`) 줄 수 0건도 함께 본다. 구체 기준은 v2 첫 과제에서 정한다.

| 현재 → 다음 | 조건 | 행위자 | 라벨 |
|---|---|---|---|
| (없음) → `queued` | 업로드 검사 통과 | 업로드한 사용자 | 현재 동작 |
| `queued` → `processing` | 처리 슬롯 확보 | 시스템 | 현재 동작 |
| `processing` → `completed` | 전사 내용 있음(항목 0건 포함) | 시스템 | [확정] 0건도 정상 완료 |
| `processing` → `no_content` | 전사가 비었거나 말소리 없음 | 시스템 | [확정] 상태 신설 / [제안] 코드 값 |
| `processing` → `failed` | 엔진 오류·Kill·재시작 중단 | 시스템 / 관리자 | 현재 동작 |
| `failed` → `queued` | Retry | 관리자 | 현재 동작 |
| `no_content` → ? | 파일 확인 뒤 재업로드 또는 종결 | 업로드한 사용자 / 관리자 | [제안] Retry 허용 여부는 v2 첫 과제에서 결정 |

### 3.3 회의록 상태 흐름
- **[제안]** 회의록 상태:

```
draft(작성 중) ──공개──▶ in_review(확인 중) ──모든 항목 확정──▶ settled(확정)
                              │                                   │
                              └──────── 정정(correction) ◀────────┘
                                         (상태는 유지, 정정 사건만 추가)
```

| 상태 | 뜻 |
|---|---|
| `draft` | 추출 결과를 바탕으로 회의록을 만드는 중. 지시자·실무 수행자 명기 전. **자동 확정 시계는 이미 돌고 있다**(아래 기산점). |
| `in_review` | 지시자(관리자)·실무 수행자 명기 완료, 참석자·담당자 확인 대기. 시계는 `draft`에서 이어서 계속 간다. |
| `settled` | 모든 항목이 확정됨(사람 확인이든 자동이든). |

- **[확정]** 자동 확정 기산점은 "회의록 최초 생성 시각"이다. 검토·수정 중에도 시계는 계속 가고, 수정해도 리셋되지 않는다(부록 A-7, 기산점 명시는 사용자 결정 2026-09-30). `draft`→`in_review` 전환(공개)이나 정정은 기산점이 아니다.
- **[제안]** "회의록 최초 생성 시각"은 `minutes_created` 사건의 `occurred_at`으로 기록하고, 회의록 행의 `first_created_at`은 이 값을 한 번만 쓴다(이후 변경 없음).
- **[제안]** (b) 초안 방치 경고(선택 기능): `draft` 상태로 일정 시간(예: 생성 후 1일, 또는 자동 확정까지 남은 시간이 기간의 절반 이하)이 지난 회의록을 작성자·관리자에게 시스템 안내로 경고한다. 경고는 `notice_raised`(사유 `draft_stale`)로 기록하며 시계를 멈추거나 늦추지 않는다. 경고 기준 시간은 고객사 정책값.
- **[확정]** 담당자가 확인한 뒤에도 담당 관리자가 회의록을 수정·정정할 수 있고 이력은 보관한다(부록 A-8). → **[제안]** 정정은 상태를 되돌리지 않고 "정정 사건"을 추가하는 것으로 표현한다. `settled`인 회의록도 정정 가능.
- **[제안]** 회의록은 회의 1건당 1개를 기본으로 하되, 표에서는 `minutes_id`를 회의 ID와 분리해 둔다(재전사·재작성 시 여러 판본 가능).

### 3.4 항목 확정 상태
- **[제안]**

```
pending(확정 대기) ──본인/관리자 확인──▶ confirmed(확정, kind=self|manager)
       │
       ├──기간 경과──▶ confirmed(kind=period_elapsed)
       ├──마감 도래──▶ confirmed(kind=due_reached)
       ├──관리자 종결──▶ closed
       └──삭제──▶ deleted(행은 남기고 상태만)
```

| 현재 → 다음 | 조건 | 행위자 | 라벨 |
|---|---|---|---|
| (없음) → `pending` | 회의록 최초 생성(`minutes_created`) 때 항목 생성. 자동 확정 예정 시각도 이때 계산 | 회의록 작성자(관리자) / 시스템 | [확정] 기산점 / [제안] 생성 시점 |
| `pending` → `confirmed(self)` | 참석자 또는 비참석 실무 책임자가 로그인해 확인 클릭 | 해당 계정 본인 | [확정] 확정 주체(부록 A-6) / [제안] kind 구분 |
| `pending` → `confirmed(manager)` | 그 업무의 관리자가 로그인해 확인 | 관리자 | [확정] 확정 주체 / [제안] kind 구분 |
| `pending` → `confirmed(period_elapsed)` | 회의록 최초 생성 시각 + N일 도달, 마감일이 더 늦거나 없음(회의록이 `draft`여도 적용, 처리 방식은 5.3 (a)) | 시스템 | [확정] 규칙(부록 A-7) / [제안] `draft` 중 도달 처리 |
| `pending` → `confirmed(due_reached)` | 마감일 도달, 마감일이 더 빠름 | 시스템 | [확정] 규칙(부록 A-7) |
| `pending`/`confirmed` → `closed` | 관리자 종결 | 관리자 | [제안] (메일 중단 사유로 부록 A-10이 "관리자 종결"을 언급) |
| 어느 상태 → `deleted` | 삭제 | 관리자 | [제안] 행 삭제가 아닌 상태 + 사건 기록 |
| `confirmed` → `confirmed`(내용 정정) | 정정 | 담당 관리자 | [확정] 정정 가능(부록 A-8) / [제안] 확정 상태는 유지, 정정 사건 추가 |

- **[제안]** 회의록이 `draft`(초안)인 동안 그 항목은 사람이 확정할 수 없고(`self`/`manager` 확인 불가), 자동 확정 시계만 진행한다. 확인 대상자에게 항목이 보이는 것은 공개(`in_review`) 이후다. 공개 시점에 이미 자동 확정 시각이 지난 항목은 5.3의 (a)안(a-1~a-3 중 선택)을 따른다.
- **[확정]** 확정 주체 중 누구든 한 명이 확인하면 확정된다(부록 A-6). → **[제안]** 확정 뒤에도 나머지 사람의 "확인" 클릭은 별도 확인 사건으로 계속 기록한다(누가 봤는지 남기기 위해). 확정 상태는 바뀌지 않는다. → 부록 C로 대체됨
- **[제안]** 항목 진행 상태(현재의 `open/in_progress/done/overdue`)는 확정 상태와 별개 열로 유지한다. `overdue`는 저장값이 아니라 마감일과 오늘 날짜로 계산하는 값으로 바꾼다(현재는 저장값이며 계산 코드 없음, `app/db.py`·`app/seed.json`).

## 5) 자동 확정 규칙

### 5.1 확정된 규칙
- **[확정]** 회의록 최초 생성일 기준 기본 5일(촉박하면 10일, 고객 설정값). 업무 마감일이 더 빠르면 마감일에 확정한다(둘 중 빠른 쪽, 항목 단위). 수정해도 기간은 리셋하지 않는다(부록 A-7).
- **[확정]** 기산점은 "회의록 최초 생성 시각"이다. 검토·수정 중에도 시계는 계속 가고, 수정해도 리셋되지 않는다(사용자 결정 2026-09-30, 3.3과 같은 문구).

**[제안] "N일" 계산 방식 비교** (결론 없음)

| 비교 항목 | 방식 1: 달력일 기준 | 방식 2: 24시간 × N |
|---|---|---|
| 도달 시점 | 생성 날짜 + N일째 날이 끝나는 자정 | 생성 시각 + N × 24시간 |
| 기준 시간대 | 생성 날짜를 정할 때 필요(고객사 시간대, 기본 KST) | 계산에는 불필요, 화면 표시만 KST |
| 마감일과 min() 비교 단위 | 날짜 대 날짜(마감일 `due_date`가 날짜라 그대로 비교) | 시각 대 시각(마감일을 KST 시각으로 바꾸는 규칙 필요) |
| 생성 시각에 따른 실제 기간 | 같은 날 생성분은 같은 시각에 도달(오전 생성분이 더 김) | 모든 회의록이 같은 길이 |
| 영업일 기준(5.4)과의 결합 | 쉬움(날짜 단위로 휴일 처리) | 어려움 |

- **[제안]** 권고안: 방식 1(달력일, KST, 마감일과 날짜 단위로 비교). 어느 방식이든 `policy_snapshot`에 계산 방식과 시간대를 기록한다.

### 5.2 계산 의사코드
**[제안]**

```
auto_confirm_at(item) =
    base   = minutes.first_created_at + N일      # first_created_at = 회의록 최초 생성 시각(공개 시각 아님)
                                                  # N = 고객사 정책값(기본 5, 설정 시 10)
    due    = item.due_date (마감일 당일의 확정 시각, 5.4 참고)
    if due 가 비어 있음:  return (base, 'period_elapsed')
    if due < base:        return (due,  'due_reached')
    else:                 return (base, 'period_elapsed')

# 정정으로 due_date 가 바뀌면 auto_confirm_at 은 다시 계산하지만
# base 의 기준(first_created_at)은 바꾸지 않는다  ← [확정] 기간 리셋 없음
```

- **[제안]** 확정 예정 시각은 회의록 최초 생성(`minutes_created`) 시 사건에 기록하고, 정정으로 마감일이 바뀌면 `item_corrected` 사건에 새 예정 시각을 기록한다. 공개(`minutes_published`)는 예정 시각을 바꾸지 않는다.
- **[제안]** 이미 사람이 확정한 항목은 자동 확정 사건을 만들지 않는다.

### 5.3 경계 상황(제안 단계 선택지)

### 5.4 시각 기준(제안 단계 선택지)
- **[제안]** 영업일/달력일 기준: (a) 달력일(단순, 주말·휴일에도 확정) (b) 영업일(공휴일 달력 필요, 고객사별 휴일 관리 필요). 어느 쪽이든 사건에 기준을 기록(`policy_snapshot`).
- **[확정]** 기산점은 "회의록 최초 생성 시각"(`draft` 생성 시각)이다. 검토·수정 중에도 시계는 계속 가고, 수정해도 리셋되지 않는다. (초안 작성이 늦어지면 실제 확인 기간이 줄어드는 문제는 5.3 (a)·(b)의 [제안]으로 다룬다.)

## 6) 안내 설계

### 6.1 1차 안내(시스템 안)
- **[확정]** 변경이 생기면 시스템 안에서 로그인 시 확인할 사항을 안내한다(부록 A-9). 로그인 시 계정별 할 일 목록을 제공한다(부록 A-3).
- **[제안]** 안내 대상: 회의록 공개 시 확인 대상자 전원, 정정 시 바뀐 항목의 당사자(지시자·실무 담당자·관리자). 정정 안내 범위는 아래 6.4의 제안 선택지.

### 6.2 보조 안내(메일)
- **[확정]** 미확인자에게 하루 1회. 내용은 건명 목록과 로그인 페이지 링크 하나(건별 링크 없음). 로그인해도 안내를 멈추지 않고, 확인 완료·관리자 종결·삭제될 때까지 DB에 남은 건을 계속 안내한다(부록 A-10).
- **[확정]** 메일 시스템으로 확인·결정사항을 안내하고 있음으로 본다. 더 강한 수단은 고객 요청 시 설정 또는 개발로 처리한다(부록 A-11).
- **[확정]** 초기 채널은 시스템 로그인 안내 + 이메일. 문자·카톡은 나중 연동. 건명 노출 제한 옵션은 초기 범위 제외(부록 A-12).

### 6.3 메일 대상 선정 기준
**[제안]** 하루 1회 배치에서 수신자별로 다음을 모은다.

```
for 계정 in 고객사의 활성 계정:
    건명 목록 = [항목 for 항목 in 항목들
                 if 계정 이 항목의 확인 대상자          # 참석자·비참석 실무 책임자·관리자
                 and 회의록.상태 != draft               # 공개 전 초안은 메일 대상 아님 [제안]
                 and 항목.확정 상태 == pending]           # confirmed(모든 kind)·closed·deleted 는 전원 제외 [확정]
    if 건명 목록: mail_digest_built 기록 → 발송 → mail_sent / mail_failed 기록

항목이 confirmed 가 될 때(사람 확인·자동 확정 모두):
    다음 일일 메일부터 모든 대상자의 건명 목록에서 빠짐(위 조건)
    담당 관리자에게 notice_raised(구분 item_confirmed_to_manager) 1회      # [확정] 1회 시스템 안내
                                                                       # [확정] 표시는 관리자 로그인 시 화면, 메일은 보내지 않음(사용자 승인 2026-10-01)
```

- **[확정]** 로그인 여부는 대상 선정에 쓰지 않는다(로그인해도 안내를 멈추지 않음, 부록 A-10).
- **[확정]** 항목이 confirmed가 되면(사람 확인·자동 확정 모두) 모든 대상자의 일일 메일 목록에서 즉시 제외한다(출처: 팀장 회신 2026-10-01, 8절 A·C).
- **[제안]** 발송 단위는 수신 계정별 하루 1통, 건명에 넣을지는 항목 단위(항목 확정 상태)로 판정한다. 계정별 확인 여부로 판정하지 않는다.
- **[확정]** 담당 관리자에게는 확정 사실을 1회, 시스템으로 안내한다(출처: 팀장 회신 2026-10-01, 부록 B-1).
- **[확정]** 위 관리자 안내는 관리자 로그인 시 화면에 표시하고, 메일은 보내지 않는다(출처: 사용자 승인 2026-10-01. 팀장 회신 원문에는 없던 구체화).
- 참고: 선택되지 않은 안(계정 단위, 각 대상자가 본인 확인할 때까지 메일 계속)은 8절 C 표에만 남긴다.
- **[제안]** 같은 날 두 번 발송되지 않도록 (고객사, 수신 계정, 날짜)로 한 번만 발송(멱등).

## 부록 C. 서비스 정책 추가 (2026-10-01, 사용자 확정)

### C-1 역할
- 지시자(임원급, 지시·확인) > 중간관리자(지시자 지시를 받아 담당자를 지시·관리) > 담당자(실행).
- "관리자 이상" = 중간관리자 또는 지시자.

### C-2 원장과 원천 문서
- 원장은 회의록이다.
- 고객사가 올린 회의록·작업지시서 등은 회의록과 동등한 "원천 문서(source document)"이며, 업무는 원천 문서에 연결한다.
- 고객은 회사이며, 회사의 고객은 접근할 수 없다(예외는 건별).
- 회사·기관의 결정은 상급자 지시로 정해지고, 시스템은 그대로 처리한다.
- 고객사 업로드 문서 기반 업무는 우선 수동 등록한다(AI 추출은 후속).

### C-3 회의록 확정
- 음성 → 회의록·업무 자동 생성, 관리자 이상(지시자 또는 중간관리자)이 확인하면 확정.
- 중간관리자 등록 = 등록 시 확정(담당자 수정 요청 가능).
- 지시자 등록 = 등록 시 확정(중간관리자·담당자 수정 요청 가능).
- 담당자(일반) 등록 = "확정 대기", 관리자 또는 지시자가 결정.
- 담당자 확인(인지)은 열람 기록일 뿐 확정을 유예하지 않으며, 담당자는 수정 요청(코멘트)만 가능.

### C-4 수정 요청과 자동 확정
- 수정 요청은 상태가 아닌 기록된 이벤트이며, 자동 확정 시계를 멈추지 않는다.
- 관리자 이상의 결정이 최종이며, 충돌 시 상위(지시자) 우선.
- 자동 확정(회의록 최초 생성일+N일과 업무 마감일 중 이른 날, N 기본 5/10 고객별)은 백스톱으로 유지하며, 수정해도 시계를 초기화하지 않는다.

### C-5 업무 필수 항목
- 업무명·담당자 필수. 기한은 날짜 또는 "미확정" 중 하나.
- "미확정"은 관리자가 선택한 값이므로 경고하지 않는다. 값이 비어 있을 때만 빨간 경고("보완 필요").
- 회의록 확정과 업무 확정을 분리한다: 회의록은 정책대로 확정, 업무는 필수 항목이 모두 채워져야 확정.
- 보완 필요 업무는 자동 확정하지 않고, 관리 중인 관리자에게 일 1회 메일·로그인 할 일 표시(채우거나 삭제할 때까지).
- 기한 미확정 업무의 자동 확정 기준일은 생성일+N일만 사용한다. 마감 임박·지연 알림은 날짜 확정 전까지 없다. 관리자 화면에 "기한 미확정 N건" 집계.
- "보완 필요 (N건)"은 업무 상태에서 계산한 표시이며, 회의록 상태는 전사/추출 중 → 확정 대기 → 확정 완료.

### C-6 알림
- 회의록 생성·등록 즉시 임시 메일 1회(제목+로그인 링크만, 수신자 = 관련 지시자·중간관리자·담당자).
- "관리자 확정 후 발송"은 고객사 요청 시 확장(고객별 정책 슬롯만 확보).
- 기존 규칙 유지:
  - 로그인 시 할 일 안내.
  - 미확정자 일 1회 메일(확정·종결·삭제 시 중단).
  - 확정(자동 확정 포함) 시 해당 건 메일 중단.
  - 담당 관리자에게 로그인 시 1회 시스템 안내(메일 없음).
  - 자동 확정 건은 "자동 확정됨(미열람)" 표시, 안내에 `confirm_kind` 포함.

### C-7 화면 구성안 [제안, 구현은 프론트 연결 단계]
- `/meetings` 목록: 일시·회의명·등록자·원천·상태 뱃지. 필터: 내가 지시한 회의 / 내가 담당인 회의 / 보완 필요.
- `/meetings/{id}` 상세:
  - 개요·요약·결정사항.
  - 업무 원장 표 인라인 편집: 상태·업무명·담당자·완료기한·발화 근거. 빈칸은 빨간 테두리. 기한은 달력 + [미확정] 체크 시 회색 뱃지.
  - 전사·오디오 뷰어: 타임스탬프 클릭 시 재생·하이라이트.
  - 상급자 [확정] / 담당자 [수정 요청].

### C-8 적용 가정
1. 지시자·중간관리자 누구나 음성 회의록을 확정할 수 있다.
2. 결정 충돌 시 상위 직급 우선.

### C-9 구현 기준(E1~E4 확정)

- E3: 동등성 확인 전까지 stub 유지 후 폐기.
- E4: v1 `stub.db`는 1회성 이전 스크립트로 옮기며, 복사본으로 먼저 검증.

### D-1 회의록 단계와 목록 탭, 열람 범위
- 단계는 `active`(진행중) · `ended`(종료) · `on_hold`(보류) · `deleted`(삭제)이고, 판정 우선순위는 삭제 > 보류 > 종료 > 진행중이다(`app/models/closure.py`의 `meeting_phase`·`phase_condition`). 회의록 `status`와 별개의 축이다.
- 보류·종료·삭제는 `meetings` 표를 고치지 않고 별도 표(`meeting_holds`, `meeting_closures`)에서 계산한다(SQLite 에서 `meetings` 표를 다시 만들면 실패한 전례).
- 목록 `GET /api/meetings?phase=`(기본 `active`). 담당자(staff)는 `active`·`ended`만 조회하고 `on_hold`·`deleted`는 403, 관리자 이상은 4단계 모두. 응답 최상위 `availablePhases`가 이 값을 준다(관리자 이상 4개, 담당자 `active`·`ended`). 화면 탭은 이 값을 따른다.
- 열람 범위: 같은 고객사만. 관리자·지시자는 고객사 전체, 담당자는 참석·담당 업무(삭제 제외)·등록한 회의록만이며 **담당자는 보류·삭제된 회의록을 열람할 수 없다**(404). 판정은 `app/auth/access.py`의 `get_visible_meeting` 한 곳이다.
- 관련: 커밋 `2625c21`, `b0c0a39`.

### D-2 보류·재개
- `POST /api/meetings/{id}/hold`(사유 필수), `POST /api/meetings/{id}/resume`(사유 없음). 보류 상태는 `meeting_holds`(회의록당 1행: 보류 여부, 마지막 보류·재개한 사람·시각).
- 권한: 회의록 확정 권한과 같은 판정(`can_confirm_meeting`: 지시자 또는 총괄 관리자). 그 밖의 관리자·담당자 직급 403, 볼 수 없으면 404. 대상 상태는 `awaiting_confirmation`·`confirmed`만(그 밖 409), 종료·삭제된 회의록 409. 이미 보류인 회의록의 보류, 보류 중이 아닌 회의록의 재개는 멱등 200(변경·사건 없음).
- 보류 중에는 딸린 업무의 **상태를 바꾸지 않고** "보류된 회의록의 업무"로 본다: 할 일·자동 확정·메일·안내에서 빠지고, 수정·확정·종결·삭제·화자 저장·회의록 확정 등 쓰기는 409(`reject_if_locked`, 문구 "보류 중인 회의록입니다. 재개한 뒤에 다시 시도하세요").
- 재개: 진행 중 업무(`pending`·`confirmed`)의 기한(날짜·미확정 표시)을 모두 비워 "보완 필요"로 만든다(확정된 업무도 이때만 예외). 종결·삭제 업무는 그대로. 비운 업무마다 `item.updated`(`via=meeting_resumed`)를 남긴다. 확정 대기 회의록의 `auto_confirm_at`은 보류했던 기간만큼 뒤로 미룬다(남은 기간 유지). 화면은 재개 뒤 "기한을 다시 설정해야 하는 업무 N건"을 보여 주고 업무 행에서 기한(날짜 또는 "미확정")을 다시 넣는다.
- 사건: `meeting.on_hold`(사유 포함), `meeting.resumed`. 관련: 커밋 `84e28df`, `df28fcb`.

### D-3 종료(자동·직권)
- 자동 종료: 업무 종결 API 가 업무를 종결한 직후, 삭제되지 않은 업무가 1건 이상이고 **모두 종결**이면 회의록을 종료한다(구분 `auto`, 처리자 없음, 사유 없음). 업무가 하나도 없으면 종료하지 않는다(`app/services/lifecycle.py`).
- 직권 종료: `POST /api/meetings/{id}/end`(사유 필수). 권한은 `can_confirm_meeting`. 대상은 `awaiting_confirmation`·`confirmed`만(그 밖 409), 보류·삭제 중 409. 이미 종료면 멱등 200. 진행 중 업무(확정 대기·확정)를 **확정 전 업무도 함께 모두 종결**(업무마다 `item.closed`, `via=meeting_ended`)한 뒤 종료(구분 `manager`).
- 기록: `meeting_closures`(종료 구분 `auto`|`manager`·처리자·시각)와 사건 `meeting.ended`(payload 에 `endKind`, 직권 종료는 `reason`). 종료된 회의록의 쓰기는 409("종료된 회의록입니다. 수정할 수 없습니다").
- 관련: 커밋 `2625c21`.

### D-4 삭제
- 업무: `POST /api/action-items/{id}/delete`(사유 필수, 지시자·총괄만). 회의록: `POST /api/meetings/{id}/delete`(사유 필수, 지시자·총괄만, 처리 중 회의록은 409). 이미 삭제면 멱등 200.
- 행은 지우지 않고 **"삭제됨"으로 표시**한다: 업무는 `action_items.status=deleted`(+삭제자·시각), 회의록은 `meeting_closures.deleted_by/at`. 사건(`item.deleted`·`meeting.deleted`)에 사유와 처리자를 남긴다(흔적 보관).
- 회의록이 삭제되면 딸린 업무·수정 요청은 행을 그대로 두되 회의록 단계(`deleted`)로 목록·할 일·자동 확정·메일에서 빠진다. 업무가 삭제되면 그 업무에 남은 수정 요청(사건)은 수정 요청 조회·해결·할 일 "수정 요청 대기"에서 숨긴다(사건 행은 지우지 않는다). 삭제된 회의록은 관리자 이상이 상세·"삭제" 탭에서 볼 수 있다.
- 관련: 커밋 `b921e61`, `121400e`, `2625c21`.

### D-5 처리 사유
- **사유 필수 동작 5개**: 업무 삭제, 업무 종결, 회의록 보류, 회의록 삭제, 회의록 직권 종료. 직권 종료로 함께 종결되는 업무에도 같은 사유가 남는다.
- **사유 없는 동작**: 자동 종료, 재개(누가·언제만 기록), 5개 항목·참석자 직권 수정, 수기 업무 등록.
- 요청 본문 `{ "reason": 글자 }`: 앞뒤 공백을 지운 뒤 비어 있거나 2000자를 넘으면 422. 내용의 옳고 그름은 판단하지 않는다(비어 있는지만 확인).
- 저장 위치: 사건 `events.payload.reason`(처리자는 `actor_account_id`, 시각은 `created_at`). 사유 도입 전 사건에는 사유가 없고 소급하지 않는다. 조회: 회의록 상세의 `onHoldReason`·`endReason`·`deleteReason`. 화면은 사유 입력 확인 팝업을 쓴다.
- 관련: 커밋 `9237877`, `42cefc4`.

### D-6 허용 동작(allowedActions)
- **원칙**: 화면 버튼은 직급·상태를 직접 비교하지 않고 서버가 내려준 `allowedActions`로만 보이거나 숨긴다. 목록이 없거나 null 이면 모든 동작 버튼을 숨긴다. **목록은 화면 표시용이며, 서버의 거부(403·409)가 최종 안전장치다.** 판정 규칙은 새로 만들지 않고 기존 함수(`can_confirm_meeting`·`can_write_item`·`has_rank`·`reject_if_locked`)를 `app/auth/actions.py`가 그대로 부른다.
- 회의록 상세 응답 `allowedActions`(회의록 단위) 이름: `confirm_meeting`, `hold_meeting`, `resume_meeting`, `end_meeting`, `delete_meeting`, `edit_minutes`, `upload_update`, `add_item`, `edit_speakers`, `resolve_change_request`, `request_change`, `download_excel`, `view_history`.
- 상세의 각 업무 `allowedActions`(업무 단위; 다른 응답에서는 null) 이름: `confirm_item`, `close_item`, `delete_item`, `set_assignee`, `set_due`, `request_change`.
- 회의록 단위 조건(역할: 총괄 = 등록 관리자 또는 담당자 등록 회의록의 참석 관리자, 또는 지시자):

| 동작 | 누가 | 상태 조건 |
|---|---|---|
| `request_change`·`download_excel`·`view_history` | 열람 가능한 전원 | 항상 |
| `resolve_change_request` | 관리자 이상 | 항상(잠금 상태와 무관) |
| `edit_minutes`·`upload_update`·`add_item`·`edit_speakers` | 총괄·지시자 | 보류·종료·삭제가 아닐 때 |
| `confirm_meeting` | 총괄·지시자 | 잠기지 않았고 `awaiting_confirmation` |
| `hold_meeting` | 총괄·지시자 | 잠기지 않았고 `awaiting_confirmation`·`confirmed` |
| `end_meeting` | 총괄·지시자 | 잠기지 않았고 `awaiting_confirmation`·`confirmed` |
| `resume_meeting` | 총괄·지시자 | 보류 중(종료·삭제 아님), 상태 `awaiting_confirmation`·`confirmed` |
| `delete_meeting` | 총괄·지시자 | 삭제되지 않았고 처리 중(`processing`)이 아닐 때 |

- 업무 단위 조건: `request_change`는 삭제되지 않은 모든 업무(전원). 회의록이 잠기지 않았을 때만: `confirm_item`(`pending`)·`close_item`(`confirmed`)·`set_assignee`·`set_due`(`pending`·`confirmed`)는 업무 수정 권한이 있는 사람(지시자, 또는 총괄이거나 그 업무의 담당자인 관리자)에게, `delete_item`은 총괄·지시자에게. 삭제된 업무는 목록에 없다.
- 요약(관리자 이상 총괄 기준): 보류·종료·삭제 회의록에서는 쓰기 동작이 빠지고(보류는 `resume_meeting`·`delete_meeting`만 남음, 종료는 `delete_meeting`, 삭제는 읽기 동작만), 총괄이 아닌 관리자는 읽기 동작과 `resolve_change_request`·본인 담당 업무의 수정·확정·종결만, 담당자는 읽기 동작과 `request_change`만 갖는다.
- 업무 확정 버튼(`confirm_item`)은 보완 필요 업무에도 포함된다. 누르면 서버가 보완 필요 409 문구를 돌려준다(허용 목록은 보완 필요 여부를 보지 않는다).
- 참고: 홈(할 일)의 관리자 전용 카드는 아직 직급으로 판단한다(제한사항은 `CHANGELOG.md`).
- 관련: 커밋 `068240a`(서버), `10b3163`(화면, `reject_if_locked`를 `app/auth/locks.py`로 이동).

### D-7 회의록 5개 항목
- 항목: 목적(`purpose`), 주요 논의사항(`discussion`), 결정사항(`decisions`), 리스크(`risks`), 다음 안건(`next_agenda`; 응답은 `nextAgenda`). 저장은 별도 표 `meeting_minutes`(회의록당 1행; 항목 5개, `engine`·`extract_model`·`prompt_version`·생성 시각, 마지막 직권 수정자·시각).
- 생성: 음성 처리 때 AI 가 자동 작성한다. **업무 추출과 별도의 호출**(5개 항목 전용 프롬프트·고정 출력 형식)이라 5개 항목 응답이 없거나 형식이 틀려도 업무 추출 결과는 그대로 저장되고 5개 항목만 "내용없음"이 된다. 추출된 정보가 없는 항목도 "내용없음". 처리 엔진 기록은 전사 엔진 이름(`engine`, 운영 `gemini`)이다. 5개 항목이 아직 없는 회의록은 응답에 모두 "내용없음"과 `engine=null`로 오고 화면은 "아직 생성되지 않았습니다"로 안내한다.
- 기존 `summary`·`decisions` 칸은 예전 그대로 두고(값이 저장되지 않음), 상세 응답에 `minutes` 객체를 추가했다. 참석자는 새 칸 없이 기존 `meeting_participants`를 쓰고, 계정 없는 참석자는 `meeting_guest_participants`(D-9)에 둔다.
- 직권 수정 `PATCH /api/meetings/{id}/minutes`(보낸 항목만, 항목당 5000자 초과 422): 권한은 `can_confirm_meeting`(총괄·지시자), **확정 이후에도 가능**, 사유는 받지 않는다. 보류·종료·삭제 409. 비우면 "내용없음"으로 저장하고, 바뀐 항목만 변경 이력(구분 "직권 수정")에 남기며 바뀐 것이 없으면 이력도 없다.
- 관련: 커밋 `108b6bc`.

### D-8 공통 변경 이력
- 별도 이력 표를 만들지 않고 **사건 원장 `events`를 재사용**한다. 공통 구조: 대상 종류(`entity_type`)·대상 ID(`entity_id`)·구분(`event_type`)·변경자(`actor_account_id`)·시각(`created_at`)·변경 전/후(`payload.before`·`payload.after`, 바뀐 칸만). 기록은 `app/services/history.py`의 `record_change`로만 한다.
- 이력으로 보이는 구분(`HISTORY_KINDS`, 코드 → 화면 표시 이름): `minutes.overridden` → "직권 수정", `participants.overridden` → "직권 수정", `item.upload_updated` → "업무 갱신", `item.manual_added` → "직권 등록", `item.updated` → "업무 수정".
- 조회 `GET /api/meetings/{id}/history`: 열람 가능한 사람, 최신순 최대 200건(쪽 인자 없음). 응답 필드: `id`, `targetType`, `targetId`, `kind`(표시 이름), `kindCode`, `batchId`, `before`, `after`, `beforeMissing`, `viewImpact`, `changedBy`, `changedAt`.
- `beforeMissing`: `payload`에 변경 전 값이 없는 옛 사건이면 true(`before`는 빈 값, 화면은 "변경 전 기록 없음"). `viewImpact`: 참석자 변경 사건에만 있고, 참석자에서 빠진 사람이 그 회의록을 계속 볼 수 있는지(예: "열람 유지(담당 업무)", "열람 불가(참석자에서 빠져 볼 수 없게 됨)")를 담는다. `batchId`: 같은 업로드 갱신으로 생긴 이력의 묶음 식별자.
- **이력에 보이지 않는 기존 사건 종류**(원장에는 있음): `item.created`, `item.confirmed`, `item.auto_confirmed`, `item.closed`, `item.deleted`, `meeting.created`, `meeting.awaiting_confirmation`, `meeting.confirmed`, `meeting.auto_confirmed`, `meeting.on_hold`, `meeting.resumed`, `meeting.ended`, `meeting.deleted`, `meeting.speakers_updated`, `meeting.no_content`, `meeting.failed`, `job.queued`·`job.started`·`job.completed`·`job.failed`·`job.no_content`, `transcript.saved`, `change_request.created`, `change_request.resolved`.
- `item.updated`는 업무 수정 API 외에 재개로 비워진 기한(`via=meeting_resumed`)과 화자 매핑 자동 채움(`via=speaker_mapping`)도 같은 구분 "업무 수정"으로 보인다.
- 관련: 커밋 `108b6bc`, `f15427e`, `068240a`.

### D-9 엑셀 다운로드와 수정 회의록 업로드 갱신
- 다운로드 `GET /api/meetings/{id}/export`: 열람 가능한 전원, 읽기 전용 `.xlsx`. 시트·열 이름은 `app/services/export_sheets.py` 상수 한 곳에서만 정한다.
  - 시트 "회의 정보": 머리줄 `항목`·`내용`, 행 순서 `제목`·`일시`·`상태`·`등록자`·`확정 정보`·`참석자`(이름(계정 ID), 계정이 없으면 이름(미등록))·`목적`·`주요 논의사항`·`결정사항`·`리스크`·`다음 안건`.
  - 시트 "업무": 열 `업무 ID`·`업무명`·`담당자`·`담당자 계정 ID`·`기한`(날짜 또는 "미확정")·`상태`·`근거 타임스탬프`·`근거 인용문`. 삭제된 업무는 제외. 셀은 모두 글자로 저장한다(수식 실행 방지).
  - 한글 파일명은 `Content-Disposition: filename*=UTF-8''…`로 주고, 화면은 서버 헤더에 의존하지 않고 "{회의명}_회의록.xlsx"로 직접 저장한다.
- 업로드 갱신: 권한은 `can_confirm_meeting`(총괄·지시자), 보류·종료·삭제 409, 다른 고객사 404. **서버에 상태를 저장하지 않는 2단계**다.
  1. `POST /api/meetings/{id}/update-upload/preview`(multipart `file`, `choices`): 파일을 검증하고 변경 예정(업무별 변경 전·후, 건너뜀과 사유, 새 행, 참석자 변경과 열람 영향, 5개 항목 변경, 경고, 동명이인 후보)만 돌려준다. 아무것도 저장하지 않는다. 오류가 있어도 200이고 `canApply=false`.
  2. `POST /api/meetings/{id}/update-upload/apply`: 같은 파일·`choices`(`{"row:3": 계정ID, "participant:이름": 계정ID}`)로 한 번에 전부 또는 아무것도 적용하지 않는다. 오류가 있거나 동명이인 선택이 빠지면 400(목록만).
- 갱신 규칙: **확정 대기(`pending`) 업무만** 업무명·담당자·기한을 파일 내용으로 갱신한다. 확정·종결·삭제된 업무는 바꾸지 않고 사유와 함께 건너뛴다. 업무 ID 가 빈 행은 새 업무로 **목록 맨 아래에 추가**(근거 "등록자 직권 지정", D-10). **파일에 없는 업무는 삭제하지 않는다**(삭제는 사유 필수인 삭제 기능으로만). 빈 셀은 기존 값을 지우지 않는다(새 행의 빈 칸은 빈 상태 → 보완 필요). `상태`·`근거` 열은 읽기 전용이라 무시한다. 다른 회의록·없는 업무 ID 는 행 오류. 수식 셀은 계산하지 않고 무시한다(경고).
- 담당자·참석자 찾기: 계정 ID(`login_id`) 우선, 없으면 이름으로 찾는다(같은 고객사 활성 계정만). 같은 이름의 계정이 둘 이상이면 **동명이인** — 적용 전에 총괄이 선택해야 한다. 계정이 없는 이름은 업무 담당자가 될 수 없어 담당자 미지정(보완 필요)+경고(기존 업무는 기존 담당자 유지). 참석자는 계정이 없는 이름을 `meeting_guest_participants`(회의록별 이름 글자, 표시 "이름(미등록)", 열람 권한·담당자·알림과 무관)에 둔다. 참석자에서 빠지는 사람의 열람 영향은 미리보기와 이력(`viewImpact`)에 남는다.
- 회의록 5개 항목·참석자는 확정 이후에도 업로드로 바꾼다(구분 "직권 수정"). 이력은 같은 업로드를 `batchId`로 묶는다. 용량·행 수 상한은 설정값 `UPDATE_MAX_FILE_KB`(기본 2048)·`UPDATE_MAX_ROWS`(기본 1000)이며 초과·형식 오류는 서버가 판정한다(413·400).
- 관련: 커밋 `108b6bc`, `f15427e`, `febf678`.

### D-10 수기 업무 등록과 "등록자 직권 지정"
- `POST /api/meetings/{id}/action-items`(201): 총괄·지시자(`can_confirm_meeting`), 보류·종료·삭제 409, 다른 고객사 404. 전사·추출이 실패한 회의록(`failed`·`no_content`)에도 쓸 수 있다.
- 입력: 업무명(필수, 비면 422, 500자 초과 422), 담당자 계정(같은 고객사 활성 계정, 아니면 400), 기한 날짜 또는 "미확정"(날짜와 미확정을 함께 주면 400). 업로드 갱신의 새 행도 같은 방식으로 만든다.
- 근거는 **"등록자 직권 지정"**(`evidence_quote`)이고 근거 시각은 없다. 수기 업무는 AI 추출 업무와 `extract_model="manual"`로 구분하며 응답 `origin`이 `manual`(AI 는 `ai`)이다. 화면은 "수기" 글자 배지와 직권 지정 근거를 보여 준다. 등록자·시각은 변경 이력(구분 "직권 등록", `item.manual_added`)의 변경자·시각이다.
- 필수 항목 규칙과 확정 절차는 AI 업무와 같다: 담당자·기한이 비면 "보완 필요"이고 확정할 수 없다.
- 관련: 커밋 `f15427e`, `febf678`.

### D-11 열람 기록
- 저장: `meeting_views`(회의록 ID·계정 ID 복합 키, 고객사 ID, 첫 열람 시각, 마지막 열람 시각). 같은 사용자의 반복 열람은 행을 늘리지 않고 마지막 열람 시각만 갱신한다.
- 기록 시점: 회의록 **상세 조회가 성공했을 때만**(목록·전사문·404·타 고객사는 기록하지 않음). 기록이 실패해도 조회는 정상으로 응답한다(`app/services/history.py`의 `record_meeting_view`). 담당자의 열람 확인은 열람 기록일 뿐 확정을 유예하지 않는다(부록 C-3).
- 읽는 곳: ① 할 일의 "자동 확정됨(미열람)" — 확정 시각 이후 열람이 없으면 표시(`app/api/me.py`). ② 일일 메일 — 담당자별 "아직 열어 보지 않은 담당 회의록 수"(`app/jobs/daily_mail.py`). 열람해도 확정 대기·보완 필요 안내(관리자 대상)와 자동 확정 대상 선정은 바뀌지 않는다.
- 관련: 마이그레이션 `a1cba09b5031`(`meeting_views`·`notices`), 커밋 `068240a`.

### D-12 오디오 재생
- 원본은 `UPLOAD_DIR/{고객사 ID}/{uuid}.{확장자}`에 저장되고 `source_documents.file_path`(UPLOAD_DIR 기준 상대 경로)로 회의록과 연결된다. 경로는 DB 값만 쓰고 사용자 입력 경로는 받지 않으며 저장 폴더 밖은 404.

### D-13 수정 요청 흐름
- 수정 요청은 상태가 아니라 사건이다(`change_request.created`; payload `comment`(1~2000자)·`itemId`(없으면 회의록 전체)). 회의록·업무 상태와 자동 확정 시계에 영향을 주지 않는다(부록 C-4). 작성은 **열람 가능한 전원**이 할 수 있다(`POST /api/meetings/{id}/change-requests`, 대상 업무는 같은 회의록의 삭제되지 않은 업무만, 아니면 400).
- 해결(수락·반려): `POST /api/meetings/{id}/change-requests/{requestId}/resolve`(`decision` = `accepted`|`rejected`, 답변 `reason` 선택 2000자 이하). 권한은 관리자 이상(`manager` 이상)이며 허용 동작 `resolve_change_request`. 결정은 사건 `change_request.resolved`로 남고(처리자·시각·직급), **상위 직급 우선**: 이미 결정된 요청을 더 낮은 직급이 다시 결정하면 409, 같거나 높은 직급은 덮어쓴다(이전 결정 사건은 지우지 않음).
- 할 일의 "수정 요청 대기": 해결 API 와 같은 판정(관리자 이상 + 열람 가능)으로 처리할 수 있는 **미해결** 요청만, **본인이 남긴 요청은 제외**한다(`app/api/me.py`). 보류·종료·삭제 회의록의 요청은 모든 할 일에서 빠진다. 삭제된 업무의 요청은 조회·해결·할 일에서 숨긴다(D-4).
- **결정 (2026-10-06)**: 수정 요청 남기기·해결은 보류·종료·삭제 회의록에서도 허용하는 현행을 유지한다(`request_change`·`resolve_change_request`는 잠금 상태와 무관, 서버가 거부하지 않음).

### D-16 처리 상태·재처리·재시도·엔진 표시 [구현 기준]
- **처리 순서와 실패 시 남는 데이터**: 업로드(202, 음성 저장+원천 문서·회의록·작업 `queued` 생성) → 백그라운드 처리 `process_meeting`: 작업 `running` → 전사(STT) → **전사문 즉시 저장**(`transcripts`, 회의록당 1건) → 말소리 없음이면 `no_content` → 업무 추출 → 5개 항목 생성(업무 추출과 별도 호출, 실패해도 업무는 저장) → **업무 생성·5개 항목 저장·회의록 상태 결정·작업 완료를 한 트랜잭션**으로 저장. 따라서 실패한 회의록(`failed`)에는 전사문이 남을 수 있지만 AI 업무·5개 항목은 저장되지 않는다.
- **작업 상태** `jobs.status`: `queued`·`running`·`completed`·`failed`·`no_content`. `attempts`는 작업이 `running`으로 시작된 횟수(작업 1건당 보통 1). **오류 코드** `jobs.error_code`는 분류 코드만 저장한다(원본 예외 문구·키·경로 금지):

| 코드 | 뜻 |
|---|---|
| `gemini_key_missing` | 선택된 `GEMINI_KEY_MODE` 의 키가 비어 있음(다른 모드로 넘어가지 않음) |
| `upload_missing` | 보관된 음성 파일이 없음 |
| `timeout` | 시간 초과(요청 기한·파일 처리 대기) |
| `stt_file_failed` | Gemini 가 올린 음성 파일을 처리하지 못함 |
| `extraction_invalid` | 업무 추출 응답이 스키마에 맞지 않음 |
| `gemini_api_{HTTP 상태}` | Gemini API 오류(예: `gemini_api_503`, `gemini_api_429`, `gemini_api_401`) |
| `internal_error` | 그 밖의 예외 |
| `server_restarted` | 서버가 재시작되어 처리가 중단됨(시작 복구가 기록) |

- **상세 응답 `processing`**(추가 필드): 가장 최근 작업의 `status`·`errorCode`·`startedAt`·`finishedAt`(작업이 없으면 null). 분류 코드 모양(`[a-z0-9_]{1,50}`)이 아닌 값은 `internal_error`로 바꿔 내려준다. 화면(`lib/v2/processing-errors.ts`)은 코드를 한국어 이유로 풀고 코드 글자도 함께 보여 준다(일시 오류 `gemini_api_5xx`, 키 문제 `gemini_key_missing`·`gemini_api_401`·`403`, 모르는 코드는 "처리 중 오류가 발생했습니다 (코드)"). 처리 중(`processing`)이면 안내 배너와 자동 새로고침(`NEXT_PUBLIC_PROCESSING_REFRESH_SEC`, 기본 5초, 처리가 끝나면 멈추고 화면을 떠나면 요청 취소).
- **재처리** `POST /api/meetings/{id}/reprocess`(202 `{meetingId, jobId}`): 권한은 `can_confirm_meeting`(등록 관리자·지시자; 다른 관리자·담당자 403, 볼 수 없으면 404). 회의록 `status=failed`이고 보류·종료·삭제가 아닐 때만(그 밖 409), 처리 중(`queued`·`running`) 작업이 있으면 409, 보관된 음성 원본이 없으면 409("보관된 음성 파일이 없어 다시 처리할 수 없습니다…"). 새 작업(`queued`)을 만들고 회의록을 `processing`으로 돌린 뒤 **같은 처리 함수(`process_meeting`)와 같은 실행기**로 다시 돌린다(`app/services/reprocess.py`, `app/api/meeting_reprocess.py`). 전사문은 회의록당 1건을 새 결과로 바꾸고 5개 항목도 회의록당 1행을 갱신하므로 중복되지 않는다. 끝난 뒤 상태는 첫 처리와 같은 규칙(관리자·지시자 등록=등록 시 확정, 담당자 등록=확정 대기)이고 **자동 확정 시각(`auto_confirm_at`)은 바꾸지 않는다**(최초 생성일 기준, 리셋 없음). 따라서 실패한 채 오래 두어 그 시각이 이미 지났다면, 재처리로 만들어진 업무와 회의록은 다음 자동 확정 작업에서 바로 확정 대상이 된다. 허용 동작 이름 `reprocess_meeting`(총괄·지시자, 잠기지 않음, `failed`, 처리 중 작업 없음). 이력은 공통 변경 이력 구분 `meeting.reprocessed`("재처리"): 실행자·시각·이전 오류 코드(`previousErrorCode`)·새 작업 ID, 사유는 받지 않는다. 화면은 실패 배너의 "다시 처리" → 확인 창(안내: 음성이 다시 처리되며 Gemini 모드이면 외부로 전송되고 비용이 생길 수 있음, 확인 버튼 "재처리하기").
- **서버 시작 복구**: 서버가 시작될 때 `queued`·`running`으로 남은 작업을 `failed`(`server_restarted`)로, 그 회의록(`processing`)을 `failed`로 바꾼다(`recover_interrupted_jobs`, 사건 `job.failed`·`meeting.failed`). **자동 재실행은 하지 않는다.** 복구 실패는 로그에 예외 종류만 남기고 서버 시작을 막지 않는다.
- **일시 오류 자동 재시도**(`app/pipeline/retry.py`): Gemini `generate_content` 호출 하나하나에만 적용(전사·업무 추출·5개 항목 각각; 이미 성공한 단계는 다시 부르지 않음). 대상은 HTTP 500·502·503·504와 접속 오류(`httpx.ConnectError`)뿐이며 타임아웃·429·기타 4xx·키 오류는 재시도하지 않는다. 설정: `GEMINI_RETRY_MAX`(기본 2, 0이면 끔), `GEMINI_RETRY_BACKOFF_SEC`(기본 5초, 재시도마다 2배, 최대 60초). 모두 실패하면 기존과 같은 오류 코드로 `failed`. 로그에는 예외 종류·상태 코드·횟수만 남긴다. google-genai SDK 는 클라이언트에 `retry_options`를 주지 않으면 한 번만 시도하므로(앱은 주지 않는다) 이중 재시도가 없다.
- **처리 엔진 표시** `GET /api/system/engine`(로그인 필요): `{engine: "fake"|"gemini", isFake}` 만(키·키 모드·모델·기타 설정은 내려주지 않음). 서버 시작 때 `STT_PROVIDER=fake`면 "가짜(fake) 처리 모드로 실행 중" 경고 로그. 화면은 `isFake`이면 앱 틀 상단과 업로드 화면에 "시험용 가짜 처리 모드입니다. 업로드한 음성은 실제로 처리되지 않습니다."를 글자로 표시하고, 회의록 상세에는 그 회의록의 `minutes.engine`이 `fake`일 때 같은 취지의 안내를 보여 준다.
- **재처리 성공 시 자동 확정 기간 재계산 (정책 변경, 2026-10-06 승인)**: 재처리가 성공(`completed`)하면 **확정 대기** 회의록의 `auto_confirm_at`을 재처리 성공 시각 + 고객사 기간(`tenants.auto_confirm_days`)으로 다시 계산해 저장한다(첫 처리와 같은 함수 `services/processing.auto_confirm_at` 재사용, `services/reprocess.recompute_auto_confirm_after_reprocess`). 회의록의 첫 처리와 이미 확정된 회의록(등록 시 확정 등)은 바꾸지 않고, `first_created_at`(최초 생성일)도 그대로다. 업무 마감일이 더 빠른 업무는 기존 자동 확정 작업의 마감일 규칙(`due_reached`)이 따로 처리하며 회의록 시각에는 마감일을 넣지 않는다. 이전 값과 새 값은 공통 변경 이력(구분 "재처리", `meeting.reprocessed`, 단계 `completed`)에 남는다. 이로써 재처리 직후에는 자동 확정되지 않고 새 기간이 지난 뒤에 확정된다(작업 61 보고의 "곧바로 확정 대상" 동작은 이 정책으로 대체).
- **내가 올린 회의록의 처리 현황** `GET /api/me/processing`(로그인 필요, 읽기 전용, 열람 기록 없음): 현재 사용자가 등록한 회의록 중 최근 `PROCESSING_TRACK_HOURS`(기본 24)시간 안에 처리가 시작된 것(시작 전 대기 작업은 만든 시각), 삭제 단계 제외, 회의록마다 가장 최근 작업 1건, 최신순 최대 10건(같은 고객사·본인 등록분만). 항목: `meetingId`·`jobId`·`title`·`status`(`queued`|`running`|`completed`|`failed`|`no_content`)·`errorCode`(분류 코드만)·`elapsedSec`(서버가 응답 시점 기준으로 계산: 대기·처리 중은 지금까지, 끝난 작업은 시작~종료)·`finishedAt`·`canReprocess`(허용 동작 `reprocess_meeting` 판정 그대로). 화면(왼쪽 메뉴 "처리 현황", `ProcessingProvider`·`ProcessingPanel`)은 앱이 열릴 때 한 번 조회하고 업로드 직후에도 조회하며, 처리 중 항목이 있는 동안만 `NEXT_PUBLIC_PROCESSING_REFRESH_SEC` 주기로 다시 조회한다. 최대 3건만 보이고 나머지는 "외 N건", 닫은 항목은 계정별로 브라우저 저장소(localStorage, 작업 번호 기준)에 기억하며 저장소가 막혀도 동작한다. 완료·실패 전환을 감지하면 그 회의록 상세를 보고 있을 때 상세를 조용히 다시 불러온다(팝업·입력값은 유지).
- **3단계 진행 표시(전사 → 업무 추출 → 5개 항목)는 V3.0 과제**다. 현재는 "처리 중 · 경과 mm:ss" 한 단계만 표시하며 처리 단계 칸·마이그레이션은 만들지 않았다.
- 마이그레이션·새 표 없음(기존 `jobs`·`meetings`·`events`를 그대로 사용).

### D-17 근거 시각 산정과 보정 도구 [구현 기준]
- **원인(확인됨)**: 실제 Gemini 가 만든 전사문의 시각 표기는 `[mm:ss]`(예: `[00:15]`)였고(전사 프롬프트는 `[HH:MM:SS]`를 요청), 전사문은 구간(`segments`) 없이 줄 글자(`full_text`)로만 저장된다. 업무 추출이 돌려준 인용 시각 `quote.timestamp`를 초로 바꾸는 기존 변환(`timestamp_to_seconds`)은 `HH:MM:SS`만 받아 `mm:ss`는 None 이 되므로, 인용문은 저장되지만 `evidence_start_sec`이 비었다. fake 경로는 `HH:MM:SS`라 정상이었다.
- **원칙**: 근거 시각은 Gemini 응답에 맡기지 않고 **서버가 저장된 전사문의 구간 시각과 근거 인용문을 대조해서 정한다**(엔진이 로컬로 바뀌어도 같은 방식, 인용문이 전사문에 실제로 있는지 확인하는 환각 방어를 겸함). 모듈 `app/pipeline/evidence_time.py`.
- **구간**: 전사문 구간(`segments`)이 있으면 그것, 없으면 `[mm:ss]`·`[hh:mm:ss]` 줄(이어지는 줄은 앞 구간에 붙임, 화자 표기는 뺌).
- **대조 규칙**: 공백·구두점을 지운 글자로 대조한다. 인용문이 한 구간에 들어 있으면 그 구간의 시작 시각, 여러 구간에 걸치면 인용문이 시작되는 첫 구간의 시작 시각(같은 말이 여러 곳이면 Gemini 시각이 가장 가까운 쪽, 없으면 첫 번째). 완전 일치가 없으면 인용문이 이어진 구간(최대 3개)과 얼마나 맞는지를 `difflib`로 재서 가장 높은 곳을 고르되 **`EVIDENCE_MATCH_MIN`(기본 80, 0~100) 미만이면 대조 실패**.
- **최종 값**: 서버 대조 값이 있으면 그 값 > 대조 실패이고 Gemini 시각이 전사문 안(마지막 구간 시작 이하)이면 그 값 > 둘 다 없으면 비움(None). 비교할 전사문 구간이 아예 없으면 Gemini 값을 그대로 둔다. 대조 실패 건수는 로그에 건수만 남긴다(인용문 원문·키 금지).
- **적용 지점**: `process_meeting`이 업무 추출 결과를 저장하기 직전에 적용한다. 업로드 처리와 재처리가 같은 함수를 지나므로 같은 경로이고, 시각을 못 찾은 업무도 업무 자체는 저장된다. fake 경로의 결과(예: 3초·20초)는 그대로다. 새 표·칸·마이그레이션 없음.
- **기존 데이터 보정 도구** `python -m app.jobs.backfill_evidence_time [--meeting-id N] [--apply]`(backend/ 에서 실행, Gemini 호출 없음): 기본은 변경 예정 목록만 출력하는 dry-run(업무 id, 회의록 id, 새 시각 또는 "대조 실패", 인용문 앞 30자), `--apply`일 때만 저장, `--meeting-id`로 한 회의록만. 대상은 근거 시각이 비고 근거 인용문이 있는 업무이며 **근거 시각 칸만 채운다**(이미 값이 있는 업무·수기 등록 업무·삭제된 업무·삭제·보류 단계 회의록은 제외, 확정·종결 업무는 포함). 저장 때 공통 변경 이력에 구분 `evidence.backfilled`(화면 표시 이름 "근거 시각 보정", 실행자 시스템, 변경 전 None·후 값)을 남긴다. 운영 DB 에는 백업 후 사용자가 직접 실행한다.
- 관련 설정: `EVIDENCE_MATCH_MIN`(`.env`, pydantic-settings).

### D-18 DB 중립 규칙과 SQLite 설정 [구현 기준]
- **방언 의존 금지**: 앱 코드는 SQLAlchemy 표현식만 쓴다. SQLite 전용 함수·구문(strftime, json_extract, INSERT OR REPLACE, 방언별 upsert 등)과 표 재생성 우회를 새로 만들지 않는다. SQLite 전용 설정은 `app/db.py` 의 SQLite 분기 안에만 둔다. 새 표는 기존 표를 바꾸지 않는 별도 표로 추가한다.
- **SQLite 연결 설정**(연결마다): `PRAGMA busy_timeout`, `journal_mode`, WAL 이면 `synchronous=NORMAL`, `foreign_keys=ON`. 설정 이름·기본값: `SQLITE_BUSY_TIMEOUT_MS`=10000, `SQLITE_JOURNAL_MODE`=WAL(DELETE 로 되돌릴 수 있음). SQLite 가 아닌 주소면 어떤 PRAGMA 도 실행하지 않고, 메모리 DB 는 저널 모드를 바꾸지 않는다. 저널 모드 전환에 실패해도 서버는 시작되고 경고 로그만 남긴다.
- **기존 운영 DB 파일**: 서버를 다음에 시작할 때(첫 연결) WAL 로 바뀐다(파일에 기록되는 설정).
- **SAVEPOINT**: pysqlite 는 begin_nested() 와 트랜잭션 시작 시점이 어긋나므로 SQLite 분기에서 드라이버의 자동 BEGIN 을 끄고 BEGIN 을 직접 보낸다(메일 중복 방지가 savepoint 를 쓴다).
- **메일 중복 방지**: `queue_mail` 은 savepoint 안에서 넣고, dedupe_key unique 위반이면 "이미 있음" 으로 건너뛴다(다른 제약 위반은 그대로 올림).
- **합계 집계**: 회의록 목록의 보완 필요 수는 coalesce + 정수 변환으로 엔진과 무관하게 int.
- **활성 업무 조건 모듈** `app/models/item_conditions.py`: 업무 상태를 쿼리 조건으로 가르는 조건(삭제 아님·열려 있음·끝남·확정 대기·확정됨)을 이름 붙은 함수로 한 곳에 둔다. 업무 상태 직접 비교는 이 모듈 밖에 두지 않는다(`tests/test_item_conditions.py` 의 가드가 검사). 이후 "대체된 업무" 제외는 이 모듈 한 곳에만 추가한다(지금은 대체 기능이 없어 조건이 비어 있다).
- **백업 주의**: WAL 모드에서는 `-wal`·`-shm` 파일이 함께 생긴다. 서버를 끄고 파일을 복사하거나 SQLite 백업 방식을 쓴다(실행 중 DB 파일만 복사하면 최근 변경이 빠질 수 있다).
- **PostgreSQL 점검**: alembic 오프라인(`--sql`) 모드로 postgresql 방언 DDL 이 생성되는 것을 확인했다(18개 표, 마지막 리비전까지).

### D-21 프로젝트 총괄 권한과 총괄 변경 [구현 기준, 작업 66-3b]
- **권한 범위**: 프로젝트 총괄(활성 프로젝트의 `project_members` role=lead)은 그 프로젝트에 연결된 회의록(`meeting_classifications.project_id`)에서 기존 "회의록 총괄" 권한 전체를 가진다(회의록 확정, 업무 확정·수정·삭제·종결, 보류·재개, 직권 종료·삭제, 5개 항목 수정, 수정 회의록 업로드 갱신, 수기 업무 추가, 재처리, 화자 지정, 할 일의 확정 대기 목록 등). 수정 요청 해결은 원래 관리자 직급이면 열람 가능한 요청을 해결하는 규칙이라 총괄 판정과 무관하다.
- **적용 조건**: 총괄의 현재 직급이 manager 이상이고 프로젝트가 active 일 때만. 직급이 내려가거나 프로젝트가 대기·반려이면 권한이 없다. 기존 총괄 규칙(회의록 등록 관리자 등)과 지시자 권한은 그대로이며 프로젝트 총괄은 추가 경로다. 연결되지 않은 회의록·다른 프로젝트·다른 고객사에는 영향이 없고 열람 규칙은 바꾸지 않았다.

### D-24 업무 종결 구분 [구현 기준, 작업 70-1]
- **구분 값**: `completed`(정상 완료), `forced`(직권 종료). 업무 상태값은 늘리지 않았고 `action_items.status` 는 그대로 `closed` 이다. 구분은 별도 표 `item_closures`(마이그레이션 `f6c2d8a41b75`, 기존 표 변경 없음)에 둔다: id, tenant_id, item_id(유니크, 업무당 최대 1행), kind(CHECK completed·forced), closed_by, created_at.
- **종결 API**: `POST /api/action-items/{id}/close` 입력에 `closureKind`(선택)를 추가했다. 값이 있으면 허용값만 받고(아니면 422) 종결과 같은 트랜잭션에서 행을 저장한다. 값이 없으면 행을 만들지 않는다(구분 없음). 이미 종결된 업무의 재호출은 기존대로 200이며 구분 행·사건을 바꾸지 않는다. 사유 필수 규칙, 종결 권한, 종결 가능 조건, 허용 동작 이름은 그대로다.
- **구분 없음**: 구분 행이 없는 종결 업무(이전에 종결된 것, 구분 없이 종결된 것)는 "구분 없음"이며, 이후 실적 집계에서 완료로 세지 않는다(집계는 이번 범위 아님).

- **하지 않은 것**: 실적 집계, 업무 대체, 회의록 단위 종료·보류·삭제의 구분, 구분 정정 기능. `models/item_conditions.py` 는 바꾸지 않았다. downgrade 는 행이 있으면 거부한다.

  | 지시자(executive) | 전사(기본) 또는 고객사의 아무 부서 | 지정 가능 |
  | 부서장(account_departments role=head) | 본인이 부서장인 부서(없으면 이름순 첫 부서) | 본인 부서만, 다른 부서 403 |
  | 그 밖의 관리자·담당자 | 본인 개인 현황만(타인 이름·건수 없음) | 지정하면 403 |

  다른 고객사·없는 부서는 404(범위 판정보다 먼저).
- **설정**: `WORKLOAD_SNAPSHOT_ENABLED`(기본 true), `WORKLOAD_SNAPSHOT_TIME`(기본 00:10), `WORKLOAD_OVERLOAD_THRESHOLD`(기본 5, 진행 중+지연이 이 값 이상이면 `overloaded`), `WORKLOAD_URGENT_MAX`(기본 50).
- **수동 도구**: `python scripts/run_workload_snapshot.py --tenant "고객사A" [--date YYYY-MM-DD] [--apply]`. 기본 dry-run(저장하지 않고 건수 요약만), `--apply` 일 때만 저장.
- **아직 하지 않은 것**: 기간 선택, 개인 간 순위·점수화, 다운로드, 조직 관리 화면.

### D-26 자료 파일(txt) 등록 [구현 기준, 작업 73-1]
- **입력**: `POST /api/meetings/upload` 에 선택 입력 `sourceKind`(`audio` 기본, `transcript_txt`)를 추가했다. `transcript_txt` 인데 확장자가 `.txt` 가 아니면 422, 알 수 없는 값도 422. `audio`(또는 생략)로 `.txt` 를 올리면 기존대로 415(허용 음성 확장자에 txt 가 없다).
- **검증(422, 업로드 때 바로)**: 크기 `TRANSCRIPT_UPLOAD_MAX_BYTES`(기본 2MB), 인코딩(UTF-8 BOM 허용 → 실패하면 CP949 → "txt 파일의 문자 인코딩을 읽을 수 없습니다"), 빈 파일·공백뿐, NUL 바이트(바이너리), 글자 수 `TRANSCRIPT_MAX_CHARS`(기본 300000). 전사 본문은 로그·오류 문구·사건에 넣지 않는다. 저장은 `UPLOAD_DIR/{tenant_id}/{uuid}.txt`.
- **해석 규칙**(`app/pipeline/transcript_text.py`): `[mm:ss] 화자N: 내용`·`[hh:mm:ss] 이름: 내용`은 `[hh:mm:ss] 화자: 내용` 줄로 맞춰 저장한다. 시각 없는 `화자N: 내용`·`이름: 내용`도 읽는다(시각 없는 줄의 라벨은 공백·문장부호 없는 짧은 이름 또는 "화자 N"만 인정). 라벨 없는 줄은 직전 발언의 연속, 첫 줄부터 라벨이 없으면 `화자1`. 시각이 없는 줄이 있으면 구간(segments, 화자만·시각 null)을 함께 저장해 화자 목록이 만들어진다. 시각이 하나도 없으면 업무의 근거 시각은 null(엔진이 준 시각은 버린다).
- **파이프라인 차이**: STT 단계만 건너뛴다(저장 파일 확장자가 `.txt` 이면 올린 전사문을 읽음). 전사문은 `transcripts.stt_provider = "자료 파일(STT 없음)"` 로 저장, 5개 항목·업무 추출·근거 시각 산정·자동 확정 기간·상태 전이는 음성과 같다. 회의록 5개 항목의 생성 엔진(`meeting_minutes.engine`)은 추출기(STT_PROVIDER)를 따른다. 재처리는 저장된 전사문(없으면 보관된 txt)으로 추출 단계만 다시 한다.
- **자료 종류 판별**: 새 표 없이 원천 문서의 저장 파일 확장자로 판별한다(`services/source_kind.py`). 기존 회의록은 모두 audio. 마이그레이션 없음.
- **응답**: 회의록 상세에 `sourceKind`(audio|transcript_txt)·`hasAudio` 추가. 자료 파일 회의록의 `GET /audio-url` 은 404("음성 파일이 없습니다"). `meeting.created` 사건 payload 에는 txt 일 때만 `sourceKind` 를 더한다.
- **아직 하지 않은 것**: 워드·pdf 등 다른 형식(엑셀 자료 등록은 아래 "엑셀 자료 파일" 항목, 작업 84-1), 시각 없는 전사문의 화자 표시 이름 치환(원문 줄머리 치환은 시각 표기가 있는 줄만).
- **엑셀 자료 파일 [작업 84-1]**: `sourceKind=transcript_xlsx`(허용 확장자 `.xlsx` 만, `.xlsm` 은 422 "매크로 파일은 올릴 수 없습니다", 다른 확장자·종류 불일치도 422). 문서에 컬럼 규칙이 없어 **헤더 이름으로 자동 판별**한다(`app/pipeline/transcript_xlsx.py`).
  - **열**: 위쪽 10행 안에서 "발언" 열(발언·내용·대화·text 등)이 있는 행을 머리글로 본다. "시각" 열(시각·시간·타임스탬프·time 등)과 "화자" 열(화자·발언자·이름·speaker 등)은 있으면 읽는다. 머리글을 찾지 못하면 422(작업 85-1 문구: "'발언' 열을 찾지 못했습니다. 올리기 화면의 '엑셀 양식 내려받기'로 받은 양식을 사용해 주세요…"). 시각은 `mm:ss`·`hh:mm:ss` 글자, 엑셀 시간 값, 초 단위 숫자를 읽고 읽을 수 없는 값은 시각 없음. **화자 열이 없거나 칸이 비어 있으면 화자 표기 없이 원문 그대로 둔다(작업 85-1: 임의 `화자1`·직전 화자 이어 쓰기 제거).**
  - **합치기**: 보이는 시트를 순서대로 모두 읽고(숨김·빈 시트는 건너뜀) 행마다 발언 목록(`{speaker, start_sec, text}`)으로 만든다(`xlsx_to_utterances`; 글자로 합쳐 다시 해석하지 않으므로 발언 안의 콜론이 화자 구분으로 오인되지 않는다). 읽기용 글자는 `[hh:mm:ss] 화자: 발언`(화자·시각이 없으면 그 부분을 쓰지 않는다). **화자 표기는 앞뒤 공백만 다듬고 공백·문장부호를 지우지 않는다(작업 85-1; 예: "김 대리" 그대로).** 셀 안 줄바꿈은 공백 하나로 합친다.
  - **업로드 때 바로 거부(422, 저장 안 함)**: 크기 `TRANSCRIPT_UPLOAD_MAX_BYTES`, 비밀번호가 걸린 파일(OLE 컨테이너), 매크로(vbaProject·macroEnabled 포함), zip 이 아니거나 손상, 압축 해제 크기 100MB 초과, 행 10만 초과, 빈 시트·발언 없음, 글자 수 `TRANSCRIPT_MAX_CHARS` 초과. 수식은 저장된 계산 값만 읽고(값이 저장되지 않은 수식은 빈 칸) 외부 링크는 따라가지 않는다. 전사 본문은 로그·오류 문구에 넣지 않는다.
  - **파이프라인**: txt 와 같다(STT 건너뜀, `stt_provider="자료 파일(STT 없음)"`, 추출·근거 시각·재처리 동일). 시각이 하나도 없으면 근거 시각은 비운다. 자료 종류 판별은 저장 파일 확장자(`.xlsx`)이며 새 표·마이그레이션 없음. 상세 응답 `sourceKind=transcript_xlsx`·`hasAudio=false`. 라이브러리는 이미 설치된 `openpyxl` 만 쓴다.
  - **처리 단계 표시값**: 회의록 상세 `processing.stage`(추가 필드): `convert`(준비·변환: 음성 변환 또는 자료 파일 읽기)·`extract`(업무 추출)·`done`. 작업 상태와 이번 작업이 시작된 뒤의 전사문 저장 사건에서 파생하며 저장 칸은 없다.
- **자료 파일 화자 표시 규칙 [작업 85-1, txt·엑셀 공통]**: 화자 라벨이 없는 발언에는 임의 라벨(`화자1` 등)을 붙이지 않는다. 저장은 발언별 `speaker=""`(구간 `segments` 에 남기고, 시각 없거나 화자 없는 발언이 있으면 구간을 함께 저장) + 전사 줄은 `[hh:mm:ss] 발언`/`발언`. 화면(전사문·근거)에는 라벨 없이 원문 그대로 보인다. 추출 품질 원칙(담당자는 원문 근거가 있을 때만, 없으면 빈 문자열)은 그대로다. txt 에서 시각만 있고 라벨이 없는 줄도 같은 규칙(직전 화자를 이어 쓰지 않음). 이미 등록된 회의록의 저장 데이터는 바꾸지 않는다(옛 `화자1` 은 그대로 보인다).
- **엑셀 양식 [작업 85-1]**: `GET /api/templates/transcript-xlsx`(85-2: 회의 번호 경로 `/api/meetings/{meeting_id}` 와 겹치지 않도록 이동, 옛 경로 없음)(인증 필요, 시스템 관리자는 업로드와 같은 규칙으로 403)가 openpyxl 로 양식을 즉시 만들어 내려준다(저장소에 바이너리 없음). 시트1 "회의 발언": 머리글만 `시각 | 화자 | 발언`(예시 행 없음 — 빈 양식을 그대로 올려도 등록되지 않고 "발언 열이 비어 있습니다" 422). 시트2 "작성 안내": 작성법(시각 형식 mm:ss·hh:mm:ss, 화자 비워도 됨, 발언 필수, 한 행에 한 발언, 매크로·암호 금지)과 예시 표(머리글이 인식 이름이 아니라 읽기에서 건너뜀). 읽기 규칙은 "발언" 열만 필수, 시각·화자는 선택이다.
- **자료 종류 어긋남 문구 [작업 85-2]**: 음성 종류(`audio`·생략)로 `.xlsx`/`.txt` 가 올라오면 422 "자료 파일(엑셀|텍스트)입니다. 자료 종류를 확인해 주세요."(저장 안 함). 그 밖의 허용되지 않는 확장자는 기존대로 415. 올리기 화면은 확장자로 자료 종류를 자동 선택하고 어긋남을 올리기 전에 안내한다.
- **업로드 저장 파일명 규칙 [작업 76-1]**: 새로 저장하는 업로드 파일(음성·txt)은 `UPLOAD_DIR/{tenant_id}/{회의록id}_{YYYYMMDDHH}_{순번3자리}{확장자}` 로 저장한다(예: `41_2026101409_001.m4a`). 날짜·시각은 등록 시점의 `APP_TIMEZONE`(기본 한국 시간) 년월일시, 순번은 그 회의록 안의 등록 순서(001부터, 999 초과는 자릿수 증가), 확장자는 허용된 원본 확장자의 소문자. 이름은 id·숫자·확장자만으로 만들고 원본 파일명은 넣지 않는다. 폴더 구조(`{tenant_id}/`)는 그대로. 구현은 `services/upload_storage.py`.
  - **흐름**: 검증(형식·크기·빈 파일·txt 내용) → `{uuid}.part` 임시 저장 → 회의록 행 생성·flush 로 id 확보 → 최종 이름으로 옮김(`os.link`, 같은 이름이 있으면 덮어쓰지 않고 다음 순번) → 저장 경로 기록 → 같은 트랜잭션 커밋. 어느 단계든 실패하면 롤백하고 임시·최종 파일을 지운다. 검증 오류는 회의록 행·파일을 만들기 전에 반환한다.
  - **순번 보장**: 회의록 id 가 고유하므로 파일 이름이 겹치지 않고, 같은 이름이 이미 있으면 `os.link` 의 원자적 실패로 다음 순번을 쓴다. 새 표·새 칸·마이그레이션 없음.
  - **기존 파일 무시**: `uploads` 의 기존 파일과 DB 의 기존 저장 경로는 이동·변경하지 않는다. 저장 경로를 읽는 곳(처리·재처리·오디오 재생·자료 종류 판별)은 DB 의 경로를 그대로 쓰므로 옛 형식 이름도 그대로 동작한다.
  - **원래 파일명**: 별도로 보관하는 칸은 없다(제목 미입력 시 원본 파일명이 원천 문서·회의록 제목이 되는 기존 동작 그대로). 수정 회의록(xlsx) 갱신 업로드는 파일을 저장하지 않고 메모리에서 읽기만 한다.
  - **아직 하지 않은 것**: 기존 파일 일괄 이름 변경(마이그레이션), 원본 파일명 별도 보관, 한 회의록에 파일이 여러 개 묶이는 구조(현재 회의록당 원천 문서 1건이라 순번은 항상 001).

### D-27 작업 큐와 워커 [구현 기준, 작업 75-1]
- **표 `task_queue`**(마이그레이션 `b8f3a1c6d204`, 기존 표 변경 없음): `id`, `tenant_id`, `meeting_id`(회의록 FK), `status`(CHECK `PENDING`·`PROCESSING`·`DONE`·`FAILED`), `progress`(0~100, CHECK), `error_msg`(Text, 짧은 요약만), `attempts`, `started_at`, `created_at`, `updated_at`. 인덱스 `(status, created_at)`·`meeting_id`·`tenant_id`. downgrade 는 행이 있으면 거부하고 비어 있을 때만 표를 지운다. 이 표는 `services/task_queue.py` 에서만 다룬다(가드 테스트).
- **기존 `jobs` 와의 관계**: `jobs` 는 처리 상태 전이·사건·실패 코드의 원천으로 그대로 쓰고, `task_queue` 는 "워커가 가져갈 일감"만 담는다. 워커는 회의록의 대기(queued) `jobs` 행을 찾아 기존 파이프라인(`process_meeting`)을 그대로 부른다.
- **처리 방식 `PROCESSING_MODE`**: `inline`(기본, 현행: 업로드·재처리가 BackgroundTasks 로 직접 실행) / `queue`(업로드·재처리가 같은 트랜잭션에서 `jobs` 와 `task_queue` 행만 만들고 202, 처리는 단독 워커). queue 모드의 회의록 상태는 기존과 같이 `processing`, 작업은 `queued`(대기 표시 그대로). queue 모드에서는 서버 시작 때 대기·처리 중 작업을 실패(server_restarted)로 바꾸지 않는다(워커가 복구).
- **획득**: 가장 오래된 `PENDING` 을 후보로 `UPDATE ... WHERE id=? AND status='PENDING'` 의 영향 행 수가 1 일 때만 `PROCESSING`(시도 +1, `started_at`)으로 획득, 아니면 다음 후보. 회의록당 활성(PENDING·PROCESSING) 작업은 `enqueue` 가 서비스 계층에서 보장한다(있으면 기존 것을 돌려줌).
- **복구**: 시작 시 `recover_stale` — `started_at` 이 `WORKER_STALE_SECONDS`(기본 1800) 지난 `PROCESSING` 은 시도 수가 `WORKER_MAX_ATTEMPTS`(기본 3) 미만이면 `PENDING`, 이상이면 `FAILED`("워커 중단으로 실패")와 회의록·작업 실패(코드 `worker_stopped`). 워커가 죽어 `running` 으로 남은 `jobs` 행은 다시 가져갈 때 `queued` 로 되돌린다.
- **종료**: SIGINT·SIGTERM 을 받으면 현재 작업이 끝나기를 `WORKER_SHUTDOWN_GRACE`(기본 30초)까지 기다리고, 넘으면 `PROCESSING` 을 `PENDING` 으로 되돌리고 종료한다(`release_all_processing`).
- **진행률**: 시작 10 → STT(또는 txt 읽기) 끝 40 → 전사문 저장 55 → 추출 시작 85 → 완료 100.
- **GPU 해제 지점**: 음성 경로에서 STT 엔진 `release()` 직후, 추출 시작 전에 `release_gpu_memory()`(`gc.collect()` + torch 가 있고 CUDA 가 가능하면 `torch.cuda.empty_cache()`, 없거나 오류면 로그만). txt 자료 파일은 STT 가 없어 호출하지 않는다.
- **API**: `GET /api/system/engine` 에 `processingMode`·`queuePending`·`queueProcessing` 추가(기존 필드 불변).

  - **한계**: 대기 순번(`queueAhead`)은 같은 DB 전체 대기열 기준 건수라 다른 고객사 작업도 센다(내용은 노출하지 않음). 진행 중 작업의 취소·중단은 없다.

- **회의 일시와 등록 일시 [작업 88-4, 형님 승인 정책]** — 회의 일시(`meetings.held_at`, 화면 이름 "회의 일시")는 회의(상담) 등록 때 **필수 입력**이다(비어 있으면 422, 현재보다 미래면 422, 시계 오차 허용 `MEETING_AT_FUTURE_TOLERANCE_MINUTES` 기본 10분). 입력은 사용자 현지 시각 + 오프셋 ISO, 저장은 UTC 한 가지다. 등록 일시(`first_created_at`, 응답 `registeredAt`)는 서버가 UTC 로 자동 기록하고 입력·수정할 수 없으며 회의 일시와 별개로 보관한다. 상대 날짜 계산의 기준일은 회의 일시의 현지 날짜(현행 `postprocess`의 `held_at.date()`)이고, **자동 확정 기간의 기준은 기존대로 등록 일시(최초 생성) + 고객사 N일**이다(2026-10-06 승인 정책과 일치; 회의 일시로 바꾸면 옛 회의를 늦게 등록할 때 즉시 자동 확정되는 문제가 있어 결정 대기). 등록 후 회의 일시 변경은 관리자 이상만, 사유 필수, 변경 이력(`meeting.held_at_changed`)을 남기고 이미 계산된 업무 기한·등록 일시·자동 확정 시각은 다시 계산하지 않는다. 마이그레이션 없음: `held_at` 은 처음부터 NOT NULL 이라 "회의 일시가 없는 기존 회의록"은 데이터에 없고, 화면은 값이 비어 오는 경우만 "회의 일시 미입력"으로 표시하며 이때 계산은 기존 방식(등록 일시 기준)을 유지한다.

- **확장된 프로파일 구조 [작업 79-1]**(하위 호환, 기존 형식도 통과): `llm` 에 선택 필드 `license`·`tier`(주력은 반드시 `permissive`)·`note`·`options`(예: `thinking_mode=off`)·`candidates`(시험 비교 후보: `model`·`quantization`·`license`·`tier`·`selectable_by_default`·`note`)를 더하고, 프로파일에 `draft`(초안 여부)를 둔다. `tier=conditional` 후보는 `selectable_by_default` 가 거짓이어야 하며(검증), 고객 요청 시에만 쓴다. 후보에는 모델 파일·다운로드 주소를 넣지 않고 이름·양자화·라이선스 표기·비고만 둔다. 라이선스는 확인된 것만 확정 표기하고 나머지는 "모델 카드 확인 필요"로 적는다. 도구 출력(텍스트·`--json`)에 주력·옵션·후보(tier 표시)·notes·초안 여부를 보인다(선택 규칙은 불변).
- **8GB 값 고정**: `gpu_8gb` 는 현행 방식(Qwen 2.5 7B Instruct Q4_K_M, `EXTRACT_CHUNK_MAX_CHARS=6000`, `EXTRACT_CHUNK_OVERLAP_CHARS=500`, `EXTRACT_LLM_TIMEOUT_SECONDS=300`)이며 값이 `config.py` 현재 기본값과 같음을 테스트로 고정했다(이전 초안 파일의 4000/400 은 현재 기본값과 달라 기본값에 맞춤). 후보는 Gemma 4 E4B(Apache 2.0, 시험 후보) 하나다.
- **12GB 초안**: `gpu_12gb` 는 주력 Qwen3-8B Q4_K_M(Apache 2.0, 생각 모드 끔), 청크 10000/800, STT float16. 자유 라이선스 후보(`permissive`): Gemma 4 12B, Mi:dm 2.0 Base 11.5B(MIT), Kanana 1.5 8B Instruct, Qwen3-14B(모델 카드 확인 필요). 조건부(`conditional`, 고객 요청 시에만): Llama 3.x(Meta 라이선스 조건: 고지·Notice 동봉·사용 정책·월 사용자 7억 명 초과 시 별도 라이선스), Bllossom(Llama 기반, 표기 요청은 계약이 아니라는 비고). `gpu_16gb_plus` 는 12GB 와 같은 주력·후보에 청크는 기존 값(8000/600)을 유지한다(12GB 초안보다 작음, 시험 뒤 조정). 모든 값은 초안이며 EXAONE·Qwen 3B/72B·Gemma 3 이하·Gemma 4 26B 는 넣지 않았다. STT 와 LLM 직렬 처리 원칙은 모든 프로파일에서 같다.
- **아직 하지 않은 것(79-1 기준)**: 로컬 엔진 연동, 한국어 회의록 정답지 비교 시험과 최종 모델 확정, 설치 스크립트 연결.

### D-30 라이선스(사용 허가) 검증 [구현 기준, 작업 80-1]
- **성격**: 라이선스는 "사용 허가"다. 기능 활성화(외부 연동 등)는 라이선스와 별개로 프로젝트별 협의·설치 때 정하며 변경은 시스템 관리자만 한다. 그래서 라이선스에는 기능 플래그 필드가 없다(알 수 없는 payload 키는 형식 오류). 외부 인증 서버 없이 로컬 서명 파일을 검증한다. 새 표·마이그레이션 없음.
- **.lic 형식**: UTF-8 JSON `{"payload": {...}, "signature": "<base64 Ed25519>"}`. payload: `version`(1)·`license_id`·`licensee`(발급 대상)·`max_accounts`(0 이상 정수)·`issued_at`·`expires_at`(ISO-8601 UTC)·`hardware_fingerprint`(선택). 서명 대상은 payload 를 키 정렬·공백 제거(`separators=(",",":")`, UTF-8)로 정규화한 바이트라서 키 순서·들여쓰기가 달라도 같다.
- **상태 규칙**(`app/licensing/verifier.py`, 예외 없이 항상 상태 객체): `missing`(파일 없음) → `public_key_missing`(공개키 없음·읽기 실패·Ed25519 아님) → `malformed`(JSON·구조·base64 오류) → `invalid_signature` → (서명이 맞는 payload 만 신뢰) 필드 오류는 `malformed` → `hardware_mismatch`(설정 `LICENSE_REQUIRE_HARDWARE_MATCH` 가 참이고 payload 에 핑거프린트가 있을 때만) → `expired` → `expiring_soon`(남은 일수 ≤ `LICENSE_WARN_DAYS`) → `valid`. 허용 계정 수 초과는 `over_limit` 플래그로만 표시하며 상태를 바꾸지도 차단하지도 않는다. 서명 검증 전의 payload 내용(발급 대상 등)은 결과에 담지 않는다.
- **장비 핑거프린트**: 표준 라이브러리만 사용. Windows 레지스트리 `MachineGuid`, Linux `/etc/machine-id`, 읽을 수 없으면 플랫폼 노드 정보로 대체하고 경고를 담는다. 제품 고유 솔트와 함께 SHA-256 해시로만 쓰며 원시 값은 로그·응답·예외에 넣지 않는다. 고객 장비에서 `scripts/show_fingerprint.py` 로 해시를 확인해 발급 요청에 전달한다.
- **설정**: `LICENSE_PATH`(기본 `backend/data/license.lic`)·`LICENSE_PUBLIC_KEY_PATH`(기본 `backend/config/license_public.pem`, 저장소에는 실제 공개키를 넣지 않는다)·`LICENSE_WARN_DAYS`(기본 30, 0 이상)·`LICENSE_REQUIRE_HARDWARE_MATCH`(기본 false). 상대 경로는 backend 폴더 기준. 파일은 요청 시 읽되 수정 시각·크기가 같으면 캐시를 쓴다.
- **API**: `GET /api/system/license`(읽기 전용). 로그인 필요, 사용권한 중간관리자(manager) 이상만(담당자 403·미로그인 401). 시스템 관리자 개념이 아직 없어 **임시 규칙**이다. 응답: `status`·`licensee`·`maxAccounts`·`activeAccounts`·`overLimit`·`expiresAt`·`daysLeft`·`hardwareMatch`(일치 여부만)·`message`·`warnings`. 서명·키·핑거프린트 값·license_id 는 내리지 않는다. 기존 API 응답은 바뀌지 않는다.
- **발급·키 관리 절차**: 발급은 우리 쪽에서만 한다. Ed25519 키쌍(예: `openssl genpkey -algorithm ed25519`)의 **개인키는 저장소·`backend/data`·`.env` 어디에도 두지 않고** 발급 담당 장비에 별도 보관한다. 공개키(PEM)만 배포 패키지·`LICENSE_PUBLIC_KEY_PATH` 에 둔다. `scripts/issue_license.py --private-key … --licensee … --max-accounts … --expires … --out …`(출력 파일 지정 필수, 기존 파일은 `--force` 없이 덮어쓰지 않음, 개인키 값 출력 없음). 확인은 `scripts/check_license.py`. `.gitignore` 에 `*.key`·`*private*.pem`·`backend/data/license.lic` 패턴을 추가했다. 키 교체(공개키 변경) 시 기존 .lic 는 모두 `invalid_signature` 가 되므로 재발급이 필요하다.
- **만료 시 읽기 전용 적용 — 설계 메모(미구현)**: 만료(`expired`)를 차단이 아니라 읽기 전용으로 전환한다는 방침이다. 적용 시에는 요청 단위 의존성(쓰기 메서드 POST/PUT/PATCH/DELETE 에 대해 상태 확인, 로그인·조회는 허용)과 워커의 새 작업 claim 중단을 한 곳에서 판정하는 방식이 후보다. 만료 직전 유예 기간·허용 예외(로그인, 라이선스 갱신 파일 교체)와 진행 중 작업의 처리는 협의가 필요하다. 이번에는 상태 판정과 조회만 구현했고 쓰기를 막는 훅은 없다.
- **아직 하지 않은 것·한계**: 만료 시 읽기 전용 실제 적용, 계정 생성 시 허용 계정 수 차단(초과는 표시만), 시스템 관리자 화면·프론트. **시계 조작 방어 없음**: 판정 시각은 서버 시스템 시계이며 시계를 되돌리면 만료를 피할 수 있다(로컬 검증 방식의 한계). 검증 모듈은 파이썬이라 우회 가능성이 완전히 없지는 않으며 컴파일(D-30 파트 B, `docs/ops-worker.md`)은 읽기 난이도를 높일 뿐이다.

### D-31 로컬 LLM 연동과 추출 경로 [구현 기준, 작업 81-1]
- **보안 원칙**: 모든 서비스는 로컬 LLM 기반이다. 외부망 연동은 기본 OFF 이고 설치 후 변경은 시스템 관리자만 한다. 외부 AI LLM 에 기업 정보를 올리지 않는 것이 목표다. 새 표·마이그레이션 없음.
- **설정**: `LLM_PROVIDER`(auto|gemini|local|fake, 기본 `auto` = 기존처럼 `STT_PROVIDER` 를 따름 → 기본값에서 동작 불변), `LOCAL_LLM_BASE_URL`(`…/v1` 까지), `LOCAL_LLM_MODEL`, `LOCAL_LLM_API_KEY`(기본 `not-needed`), `LOCAL_LLM_JSON_MODE`(기본 true), `LOCAL_LLM_ALLOW_EXTERNAL_HOST`(기본 false), `LOCAL_LLM_MAX_OUTPUT_TOKENS`(기본 4096), 호출 제한 시간은 기존 `EXTRACT_LLM_TIMEOUT_SECONDS` 재사용. 잘못된 URL·0 이하 토큰 수·`local` 인데 주소·모델 없음은 시작 거부.
- **클라이언트**(`app/pipeline/local_llm.py`, HTTP 는 이미 설치된 httpx 사용 — 새 패키지 없음): `POST {base_url}/chat/completions`, 본문 `model`·`messages`·`temperature=0.1`·`max_tokens`(+ JSON 모드면 `response_format={"type":"json_object"}`). 서버가 400 으로 거부하면 `response_format` 없이 1회만 다시 요청하고(요청 상한 2회, 파서 교정 재시도와 별개) 이후 호출에서는 생략한다. 키가 `not-needed`·빈 값이면 인증 헤더를 보내지 않는다. 리디렉션은 따라가지 않고 https 인증서 검증은 끄지 않는다.
- **오류 분류**: 일시(transient) = 연결 실패·타임아웃·5xx·429, 영구(permanent) = 4xx(JSON 모드 거부 제외)·응답 형식 오류·주소 설정 오류. 예외 `LocalLlmError.kind`. 작업 오류 코드: `timeout`(기존 코드 재사용)·`llm_unavailable`(일시)·`llm_error`(영구)·`llm_host_blocked`(외부 주소 거부). 메시지에 주소 전체·키·요청 본문·전사 본문을 넣지 않는다. 영구 오류는 파서의 호출 재시도도 하지 않는다.
- **연결 보호와 한계**: 호스트가 루프백(localhost, 127.0.0.0/8, ::1)·사설망(10/8, 172.16/12, 192.168/16, 링크 로컬, `*.local`, 점 없는 이름)이 아니면 기본적으로 거부("외부 주소는 허용 설정이 필요합니다"). `LOCAL_LLM_ALLOW_EXTERNAL_HOST=true` 면 허용하고 서버·워커 시작 때 경고 로그(호스트 일부 마스킹). 판정은 문자열·IP 리터럴 기준이며 **DNS 조회는 하지 않는다**: 사설 IP 로 해석되는 공개 이름은 외부로, 사내 DNS 이름이 점이 있으면 외부로 판정될 수 있고 반대로 외부 IP 로 해석되는 점 없는 이름은 사설로 판정된다.
- **확인 도구**: `scripts/check_llm.py` 는 `GET {base_url}/models` 만 호출해 연결·인증·설정 모델 존재 여부를 요약한다(주소 마스킹, 추출 호출·회의 내용 전송 없음, 외부 호스트 보호 적용).
- **파이프라인 구조(파트 B)**: `LLM_PROVIDER` 가 `local` 이면(`auto` 는 `STT_PROVIDER` 를 따라 현행 그대로) 추출 단계가 [전사문 → 안건 분할(`agenda_chunker`) → 청크별 프롬프트·LLM 호출·3단계 파서(`json_parser`, 청크당 호출 최대 2회) → 병합·중복 제거·근거 인용 검증 → 현행 `ExtractionResult` 어댑터 → 기존 후처리(근거 시각·담당자 계정 매핑)·저장]을 쓴다. STT 경로와 txt 자료 파일 경로가 모두 같다. 엔진 선택은 `services/extraction_engine.py`, 로컬 추출기는 `pipeline/local_extractor.py`(서비스 파일 `processing.py` 는 호출 한 줄만 바뀜). Gemini 경로는 선택 로직과 아래 실패 표시 규칙 외에 바뀌지 않는다. 회의 일시·참석자 입력은 현행과 같다.
- **담당자 규칙 통일**: 모델 값 → 인용 발화자 → 인용문이 있는 발언의 화자 순서는 유지하되 마지막 대체값("화자 미상")은 없앴다. 식별할 수 없으면 빈 문자열이고, 기존 규칙대로 저장 때 담당자 미지정("보완 필요")이 된다.
- **실패 표시 규칙**: 일시 오류(연결 실패·타임아웃·5xx·429·Google 503 등, `pipeline/transient.py`)로 재시도를 소진했을 때 ① 로컬 경로에서 모든 청크가 실패하면 ② Gemini 경로에서 5개 항목 생성이 일시 오류로 실패하면(업무 추출의 일시 오류는 기존에도 실패) 처리를 `failed` 로 마치고 오류 코드(`timeout`·`llm_unavailable`·`llm_error`·`gemini_api_NNN`)를 남긴다. 기존 재처리·재시도 동작을 그대로 쓴다(새 표·새 상태 없음). 모든 청크가 응답 형식 문제로 실패한 경우도 기존 Gemini 형식 오류와 같게 `extraction_invalid` 로 실패한다. 정상 응답의 업무 0건·"내용없음"은 기존대로 완료이고, 일시 오류가 아닌 5개 항목 실패(형식 오류 등)는 기존대로 "내용없음"으로 완료한다.
- **처리 경고**: 일부 청크만 실패(또는 근거 미검증 업무 등)하면 처리는 완료하고 이벤트 `job.processing_warning`(작업 단위, 문구는 구간 번호·사유 분류만)으로 남기며 회의록 상세 응답에 `processingWarnings`(문자열 목록, 없으면 `[]`, 가장 최근 작업 기준) 필드를 더했다. 최근 사건 목록(`recentEvents`)에는 섞이지 않는다. 프론트 표시는 아직 없다.
- **회의 유형별 프롬프트(로컬 경로 전용)**: 유형은 `meeting_classifications` 에서 읽고 없으면 미지정. 정기·비정기·기타·미지정은 기존 프롬프트와 글자 단위로 같다. `project` 는 마일스톤·액션아이템·담당·기한 중심, `external` 은 고객 니즈·견적·계약·후속 요청을 "주요 논의사항"·"결정사항"에 담는 관점 문단을 추가한다. 5개 항목 이름과 출력 스키마는 같다.
- **엔진 표시**: `/api/system/engine` 에 `llmProvider`(fake|gemini|local)·`llmModel`(local 일 때만 모델 이름, 아니면 "")를 추가했다(주소·키 미노출). 로컬 경로로 만든 회의록 5개 항목의 엔진 값은 서버가 만든 `로컬 LLM(모델명)` 이다.
- **아직 하지 않은 것**: 프론트 경고·엔진 표시 문구, 모델 비교 시험(한국어 회의록 정답지), 화자 음성 식별, 엑셀 자료 등록, 외부 호스트 허용 변경을 시스템 관리자만 할 수 있게 하는 화면(현재는 `.env` 직접 수정).

### D-32 시스템 관리자와 관리 API [구현 기준, 작업 82-1]
- **개념**: 시스템 관리자는 사용자 등급(지시자·관리자·담당자)과 별개다. 시스템 설정 변경은 시스템 관리자만 한다. 시스템 관리자는 회의록 내용(목록·상세·전사문·검색·오디오·엑셀·이력)을 열람할 수 없고 계정·부서·사용권한 관리, 외부 연동 설정, 라이선스 확인, 장애 대응용 메타데이터만 다룬다.
- **지정 모델(파트 A)**: 사용권한(rank)에 값을 더하지 않고 별도 표 `system_admins`(`id`·`tenant_id`·`account_id` 유니크·`created_by` null 가능·`created_at`, 마이그레이션 `c4e8a2f7b913`, downgrade 는 행이 있으면 거부)로 지정한다. 기존 표는 바뀌지 않는다. 지정 대상은 활성 **staff** 계정만이며 상위 권한 계정은 거부한다("시스템 관리자는 전용 계정으로 둔다", 서비스 계층 `services/system_admin.py` 검증). 지정·해제는 공통 이력(대상 종류 account, 구분 `admin.system_admin_set`·`admin.system_admin_unset`)에 남긴다.
- **인증**: `require_system_admin` 의존성(활성 계정이면서 `system_admins` 에 있을 때만, 아니면 403). 로그인 응답과 `GET /api/auth/me` 에 `isSystemAdmin` 필드를 추가했다(추가만).
- **열람 분리 규칙**: 판정은 `app/auth/access.py` 의 `not_system_admin` 한 곳이다. `meeting_visibility`(목록·상세·전사문·오디오·엑셀·이력·수정 요청·화자·업무 수정·유사 업무·할 일·보류/종료/삭제/재처리/확정 진입이 모두 `get_visible_meeting`/`meeting_visibility` 를 거침)와 `project_visibility`(프로젝트 목록·상세·연결 회의록)가 이 조건을 함께 건다. 그 함수를 거치지 않는 경로는 같은 `is_system_admin` 을 호출한다: 내 안내(`/api/me/notices`)·처리 현황(`/api/me/processing`)·업무 현황(`/api/workload`)은 빈 결과, 회의록 업로드·프로젝트 등록은 403, 알림 메일(`queue_mail`)과 일일 메일 대상에서 제외. 응답 방식은 기존 열람 판정과 같다(볼 수 없는 회의록은 없는 것처럼 404, 목록은 빈 목록). 비 시스템 관리자의 열람 결과는 바뀌지 않는다.
- **초기 지정 도구**: `scripts/create_system_admin.py`(기본 dry-run, `--apply` 일 때만 저장, 같은 고객사 계정만, 새 전용 계정은 `--create` + 터미널 입력 비밀번호, 이력 실행자 "시스템"). 설정 `PASSWORD_MIN_LENGTH`(기본 10, 8 이상).
- **관리 API(파트 B)**: 모두 `/api/admin/...`, `require_system_admin`, 같은 고객사 범위(타 고객사 대상은 404). 코드: 403 시스템 관리자 아님, 404 없음, 409 규칙 충돌, 422 입력 검증. 삭제 API 는 없다(계정은 비활성화, 부서는 필요 없다고 판단해 만들지 않음).
  - 계정: `GET /accounts`(검색 `q`·`page`·`size`; 로그인 ID·이름·이메일·사용권한·활성·소속 부서·시스템 관리자 여부), `POST /accounts`(로그인 ID 유일 409, 비밀번호 `PASSWORD_MIN_LENGTH` 이상 422, argon2), `PATCH /accounts/{id}`(이름·이메일·사용권한·활성), `POST /accounts/{id}/password-reset`(204, 응답·이력에 비밀번호 없음), `PUT /accounts/{id}/system-admin`(`{enabled}`: 지정·해제). 규칙: 자기 자신의 비활성화·사용권한 변경 409, 부서장 계정을 관리자 미만으로 내리면 409(먼저 부서장 변경), 시스템 관리자 계정 사용권한은 staff 고정 409, 자기 자신·마지막 시스템 관리자 해제 409(잠김 방지). 비활성 계정의 로그인 거부는 기존 동작 그대로다.
  - 부서·소속: `GET /departments`(트리: parentId, 부서장·구성원, 비활성 구성원 표시), `POST /departments`(이름 고객사 내 유일 409, 상위 부서, `isExecutiveGroup`), `PATCH /departments/{id}`(이름·상위 부서, 순환 금지 409), `PUT /departments/{id}/head`, `POST /departments/{id}/members`, `POST /departments/{id}/members/{accountId}/remove`. 규칙(부서장 1명·관리자 이상·부서장 소속 제거 불가·겸직 가능)은 `services/org.py` 한 곳이며 `scripts/manage_org.py` 와 같은 함수를 쓴다.
  - 본인 비밀번호 변경: 기존에 없어서 `POST /api/auth/change-password`(현재 비밀번호 확인, 틀리면 일반 오류 400, 새 비밀번호 정책 422, 204)를 추가했다.
  - 감사 이력: 관리 변경을 공통 이력(구분 `admin.account_created`·`admin.account_updated`·`admin.password_reset`·`account.password_changed`·`admin.system_admin_set/unset`·`department.updated`)에 대상·변경 전후 값(비밀번호·해시 제외)·실행자·시각과 함께 남기고 `GET /api/admin/audit`(최신순, 쪽 나눔)으로 조회한다. 회의록 내용 이력은 섞이지 않는다.
- **외부 연동 설정(파트 C)**: 새 표 `system_settings`(`tenant_id`·`key`(CHECK: `external_llm_enabled`·`local_llm_external_host_allowed`)·`value_bool`·`updated_by`·`updated_at`, (`tenant_id`,`key`) 유니크, 마이그레이션 `d5f9b3a8c024`, downgrade 는 행이 있으면 거부). **유효값 규칙은 하나**: 시스템 관리자 설정 행이 있으면 그 값, 없으면 `.env` 값(`EXTERNAL_LLM_ENABLED`·`LOCAL_LLM_ALLOW_EXTERNAL_HOST`, 명시하지 않았으면 거짓). `.env` 가 거부라는 이유로 행을 무시하거나 행이 `.env` 보다 느슨할 수 없게 막는 규칙은 없다. 조회 `GET /api/admin/settings`(유효값과 출처 `default`·`env`·`admin`, 스위치 상태 `enforced`), 변경 `PUT /api/admin/settings/{key}`(`{value, reason}`: 사유 1~500자 필수 422, 허용 목록 밖 키 404, 즉시 반영·캐시 없음, 사유는 이력에 기록).
- **단계 적용 스위치**: `EXTERNAL_POLICY_ENFORCED`(기본 false, `.env`). 거짓이면 현행 동작 그대로(Gemini 제한 없음, 로컬 외부 주소는 `LOCAL_LLM_ALLOW_EXTERNAL_HOST` 만 따름). 참이면 외부 LLM(추출 엔진 또는 STT 엔진이 gemini)은 `external_llm_enabled` 가 참일 때만 처리하고 아니면 처리를 시작하기 전에 `failed`(오류 코드 `external_disabled`, 기존 재처리로 다시 처리 가능)로 마친다. 로컬 LLM 외부 주소는 `local_llm_external_host_allowed` 가 참일 때만 허용하고 아니면 `llm_host_blocked`. 판단은 `services/external_policy.py` 한 곳이다. 도구 `scripts/check_llm.py` 와 시작 경고 로그는 `.env` 값을 쓴다(고객사 설정과 무관한 점검용).
- **아직 하지 않은 것**: 프론트 관리 화면·승인 큐, 로그인 성공·실패 이력과 로그인 시도 제한, 통합 로그인(OIDC), 부서 삭제, 시스템 관리자 외 시스템 설정 항목(허용 키는 두 개뿐), 만료 시 읽기 전용 적용.


### D-33 지식(KMS) 연동 선반영 [작업 83-1]
- **범위**: 설정 키·호출 인터페이스·계약 스키마·문서까지. 실제 HTTP 호출·화면·API 라우터·outbox 는 아직 없다. 상세는 `docs/design-kms-integration.md`.
- **방침**: 자료는 복제하지 않고 연합 조회 우선, 권한 판단은 원본 시스템 한 곳(응답은 이미 권한을 통과한 결과만), 시스템 간 호출은 서비스 토큰 + 사용자는 `external_sub` 로만 알림(사용자 토큰 전달 금지). 외부 AI(LLM) 허용과 완전히 분리.
- **설정**: `system_settings` 허용 키에 `knowledge_integration_enabled`(기본 거짓)·`knowledge_api_endpoint`(기본 빈 값) 추가. 시스템 관리자만 변경, 사유 필수, 이력 기록(주소 전체는 이력에 남기지 않음), 행이 없으면 `.env`(`KNOWLEDGE_INTEGRATION_ENABLED`·`KNOWLEDGE_API_ENDPOINT`). 주소는 로컬 LLM 연결 보호와 같은 함수로 검사해 사설망·루프백만 허용(위반 422). 마이그레이션 `e6a0c4b9d135`(CHECK 확장 + `value_text`, 기존 마이그레이션 불변, downgrade 는 새 키 행이 있으면 거부, PostgreSQL 오프라인 DDL 확인). `GET /api/admin/settings` 의 `items` 는 기존 두 키 그대로, 지식 키는 추가 칸 `knowledge`.
- **인터페이스**: `app/integrations/knowledge.py` `KnowledgeClient.search_references(query, external_sub, limit=3)`, `NullKnowledgeClient`(꺼짐·구현 전: 호출 없음), `FakeKnowledgeClient`. 자동 전달 코드 없음(사용자 버튼 클릭 때의 검색어만).
- **계약**: `docs/contracts/meeting-search-v1.json`·`knowledge-reference-v1.json` + 예시(정상·잘못됨). 원본 모델 `app/integrations/contracts.py`(jsonschema 미설치로 모델과 파일 일치를 테스트).
- **아직 하지 않은 것**: 실제 호출 구현·캐시(사용자별 메모리 1~3분)·화면("관련 규정 보기")·KMS 용 검색 라우터·서비스 토큰 운영 절차·복제(선택, 필수 요건은 설계 문서 6절)·outbox.
