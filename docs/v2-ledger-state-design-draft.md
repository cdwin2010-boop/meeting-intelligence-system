## 1) 전제와 범위

### 1.1 전제
- **[확정]** 제품 정체성은 임원을 위한 실행 관리 어시스턴트이며, 핵심 회의와 해야 할 일의 체크·리마인드·점검·최종 실적을 다룬다(부록 A-1).

## 3) 상태 모델

### 3.1 상태를 나누는 축
- **[제안]** 서로 다른 세 축을 한 열에 섞지 않는다.
  1. **처리 작업 상태**(현재 `jobs.status`): 음성 → 전사 → 추출 파이프라인의 진행.
  2. **회의록 상태**: 회의록 문서의 생애(작성 중 → 확인 중 → 확정 …).
  3. **항목 확정 상태 / 항목 진행 상태**: 항목별 확정 여부와, 확정 뒤 실행(진행·완료·종결) 여부.
- 현재는 처리 작업 상태(`queued/processing/completed/failed`, `app/schemas/models.py` `AdminJob.status`)와 액션아이템 진행 상태(`open/in_progress/done/overdue`, `app/schemas/models.py` `ActionItem.status`)만 있고, 회의록 상태·확정 상태는 없다.

### 3.2 처리 작업 상태(무음 상태 추가)
- **[확정]** 무음·전사가 빈 파일은 failed도 completed도 아닌 별도 상태 "내용 없음, 파일 확인 요청"으로 한다. 전사는 정상인데 액션아이템이 0건이면 이 상태가 아니라 정상 완료다. v2 첫 과제로 이관한다(부록 A 추가 결정).
- **[제안]** 코드 값 `no_content`, 화면 라벨 "내용 없음, 파일 확인 요청". 상태 점 색은 회색 계열(Mono Dark 규칙상 유채색은 Blue/Teal/Red만 쓰므로), 반드시 글자 라벨과 함께 표시.
- 현재 코드와 문서의 차이(확인함):
  - 코드: 전사가 비었거나 정확히 `[NO_SPEECH]`이면 `failed` + 사유 "말소리가 감지되지 않았습니다…" (`app/pipeline/service.py` 451~453행, 테스트 `tests/test_pipeline.py` `test_no_speech_fails_job_with_reason_and_keeps_file`).
  - `CHANGELOG.md` v1.10.0 "알려진 제한사항": 실제 무음 파일은 `completed`·0건으로 끝났다고 기록. 이 차이의 원인(예: Gemini가 `[NO_SPEECH]` 대신 다른 글자를 돌려준 경우)은 **확인 못 함**.
  - **[제안]** 판정 기준은 "모델이 정확히 `[NO_SPEECH]`를 돌려줬는가"에만 기대지 말고, 전사 줄 형식(`[HH:MM:SS] 화자: 내용`) 줄 수 0건도 함께 본다. 구체 기준은 v2 첫 과제에서 정한다.

| 현재 → 다음 | 조건 | 행위자 | 라벨 |
|---|---|---|---|
| (없음) → `queued` | 업로드 검사 통과 | 업로드한 사용자 | 현재 동작 |
| `queued` → `processing` | 처리 슬롯 확보 | 시스템 | 현재 동작 |
| `processing` → `completed` | 전사 내용 있음(항목 0건 포함) | 시스템 | [확정] 0건도 정상 완료 |
| `processing` → `no_content` | 전사가 비었거나 말소리 없음 | 시스템 | [확정] 상태 신설 / [제안] 코드 값 |
| `processing` → `failed` | 엔진 오류·Kill·재시작 중단 | 시스템 / 관리자 | 현재 동작 |
| `failed` → `queued` | Retry | 관리자 | 현재 동작 |
| `no_content` → ? | 파일 확인 뒤 재업로드 또는 종결 | 업로드한 사용자 / 관리자 | [제안] Retry 허용 여부는 v2 첫 과제에서 결정 |

### 3.3 회의록 상태 흐름
- **[제안]** 회의록 상태:

```
draft(작성 중) ──공개──▶ in_review(확인 중) ──모든 항목 확정──▶ settled(확정)
                              │                                   │
                              └──────── 정정(correction) ◀────────┘
                                         (상태는 유지, 정정 사건만 추가)
```

| 상태 | 뜻 |
|---|---|
| `draft` | 추출 결과를 바탕으로 회의록을 만드는 중. 지시자·실무 수행자 명기 전. **자동 확정 시계는 이미 돌고 있다**(아래 기산점). |
| `in_review` | 지시자(관리자)·실무 수행자 명기 완료, 참석자·담당자 확인 대기. 시계는 `draft`에서 이어서 계속 간다. |
| `settled` | 모든 항목이 확정됨(사람 확인이든 자동이든). |

- **[확정]** 자동 확정 기산점은 "회의록 최초 생성 시각"이다. 검토·수정 중에도 시계는 계속 가고, 수정해도 리셋되지 않는다(부록 A-7, 기산점 명시는 사용자 결정 2026-09-30). `draft`→`in_review` 전환(공개)이나 정정은 기산점이 아니다.
- **[제안]** "회의록 최초 생성 시각"은 `minutes_created` 사건의 `occurred_at`으로 기록하고, 회의록 행의 `first_created_at`은 이 값을 한 번만 쓴다(이후 변경 없음).
- **[제안]** (b) 초안 방치 경고(선택 기능): `draft` 상태로 일정 시간(예: 생성 후 1일, 또는 자동 확정까지 남은 시간이 기간의 절반 이하)이 지난 회의록을 작성자·관리자에게 시스템 안내로 경고한다. 경고는 `notice_raised`(사유 `draft_stale`)로 기록하며 시계를 멈추거나 늦추지 않는다. 경고 기준 시간은 고객사 정책값.
- **[확정]** 담당자가 확인한 뒤에도 담당 관리자가 회의록을 수정·정정할 수 있고 이력은 보관한다(부록 A-8). → **[제안]** 정정은 상태를 되돌리지 않고 "정정 사건"을 추가하는 것으로 표현한다. `settled`인 회의록도 정정 가능.
- **[제안]** 회의록은 회의 1건당 1개를 기본으로 하되, 표에서는 `minutes_id`를 회의 ID와 분리해 둔다(재전사·재작성 시 여러 판본 가능).

### 3.4 항목 확정 상태
- **[제안]**

```
pending(확정 대기) ──본인/관리자 확인──▶ confirmed(확정, kind=self|manager)
       │
       ├──기간 경과──▶ confirmed(kind=period_elapsed)
       ├──마감 도래──▶ confirmed(kind=due_reached)
       ├──관리자 종결──▶ closed
       └──삭제──▶ deleted(행은 남기고 상태만)
```

| 현재 → 다음 | 조건 | 행위자 | 라벨 |
|---|---|---|---|
| (없음) → `pending` | 회의록 최초 생성(`minutes_created`) 때 항목 생성. 자동 확정 예정 시각도 이때 계산 | 회의록 작성자(관리자) / 시스템 | [확정] 기산점 / [제안] 생성 시점 |
| `pending` → `confirmed(self)` | 참석자 또는 비참석 실무 책임자가 로그인해 확인 클릭 | 해당 계정 본인 | [확정] 확정 주체(부록 A-6) / [제안] kind 구분 |
| `pending` → `confirmed(manager)` | 그 업무의 관리자가 로그인해 확인 | 관리자 | [확정] 확정 주체 / [제안] kind 구분 |
| `pending` → `confirmed(period_elapsed)` | 회의록 최초 생성 시각 + N일 도달, 마감일이 더 늦거나 없음(회의록이 `draft`여도 적용, 처리 방식은 5.3 (a)) | 시스템 | [확정] 규칙(부록 A-7) / [제안] `draft` 중 도달 처리 |
| `pending` → `confirmed(due_reached)` | 마감일 도달, 마감일이 더 빠름 | 시스템 | [확정] 규칙(부록 A-7) |
| `pending`/`confirmed` → `closed` | 관리자 종결 | 관리자 | [제안] (메일 중단 사유로 부록 A-10이 "관리자 종결"을 언급) |
| 어느 상태 → `deleted` | 삭제 | 관리자 | [제안] 행 삭제가 아닌 상태 + 사건 기록 |
| `confirmed` → `confirmed`(내용 정정) | 정정 | 담당 관리자 | [확정] 정정 가능(부록 A-8) / [제안] 확정 상태는 유지, 정정 사건 추가 |

- **[제안]** 회의록이 `draft`(초안)인 동안 그 항목은 사람이 확정할 수 없고(`self`/`manager` 확인 불가), 자동 확정 시계만 진행한다. 확인 대상자에게 항목이 보이는 것은 공개(`in_review`) 이후다. 공개 시점에 이미 자동 확정 시각이 지난 항목은 5.3의 (a)안(a-1~a-3 중 선택)을 따른다.
- **[확정]** 확정 주체 중 누구든 한 명이 확인하면 확정된다(부록 A-6). → **[제안]** 확정 뒤에도 나머지 사람의 "확인" 클릭은 별도 확인 사건으로 계속 기록한다(누가 봤는지 남기기 위해). 확정 상태는 바뀌지 않는다.
- **[제안]** 항목 진행 상태(현재의 `open/in_progress/done/overdue`)는 확정 상태와 별개 열로 유지한다. `overdue`는 저장값이 아니라 마감일과 오늘 날짜로 계산하는 값으로 바꾼다(현재는 저장값이며 계산 코드 없음, `app/db.py`·`app/seed.json`).

## 5) 자동 확정 규칙

### 5.1 확정된 규칙
- **[확정]** 회의록 최초 생성일 기준 기본 5일(촉박하면 10일, 고객 설정값). 업무 마감일이 더 빠르면 마감일에 확정한다(둘 중 빠른 쪽, 항목 단위). 수정해도 기간은 리셋하지 않는다(부록 A-7).
- **[확정]** 기산점은 "회의록 최초 생성 시각"이다. 검토·수정 중에도 시계는 계속 가고, 수정해도 리셋되지 않는다(사용자 결정 2026-09-30, 3.3과 같은 문구).

**[제안] "N일" 계산 방식 비교** (결론 없음)

| 비교 항목 | 방식 1: 달력일 기준 | 방식 2: 24시간 × N |
|---|---|---|
| 도달 시점 | 생성 날짜 + N일째 날이 끝나는 자정 | 생성 시각 + N × 24시간 |
| 기준 시간대 | 생성 날짜를 정할 때 필요(고객사 시간대, 기본 KST) | 계산에는 불필요, 화면 표시만 KST |
| 마감일과 min() 비교 단위 | 날짜 대 날짜(마감일 `due_date`가 날짜라 그대로 비교) | 시각 대 시각(마감일을 KST 시각으로 바꾸는 규칙 필요) |
| 생성 시각에 따른 실제 기간 | 같은 날 생성분은 같은 시각에 도달(오전 생성분이 더 김) | 모든 회의록이 같은 길이 |
| 영업일 기준(5.4)과의 결합 | 쉬움(날짜 단위로 휴일 처리) | 어려움 |

- **[제안]** 권고안: 방식 1(달력일, KST, 마감일과 날짜 단위로 비교). 어느 방식이든 `policy_snapshot`에 계산 방식과 시간대를 기록한다.

### 5.2 계산 의사코드
**[제안]**

```
auto_confirm_at(item) =
    base   = minutes.first_created_at + N일      # first_created_at = 회의록 최초 생성 시각(공개 시각 아님)
                                                  # N = 고객사 정책값(기본 5, 설정 시 10)
    due    = item.due_date (마감일 당일의 확정 시각, 5.4 참고)
    if due 가 비어 있음:  return (base, 'period_elapsed')
    if due < base:        return (due,  'due_reached')
    else:                 return (base, 'period_elapsed')

# 정정으로 due_date 가 바뀌면 auto_confirm_at 은 다시 계산하지만
# base 의 기준(first_created_at)은 바꾸지 않는다  ← [확정] 기간 리셋 없음
```

- **[제안]** 확정 예정 시각은 회의록 최초 생성(`minutes_created`) 시 사건에 기록하고, 정정으로 마감일이 바뀌면 `item_corrected` 사건에 새 예정 시각을 기록한다. 공개(`minutes_published`)는 예정 시각을 바꾸지 않는다.
- **[제안]** 이미 사람이 확정한 항목은 자동 확정 사건을 만들지 않는다.

## 6) 안내 설계

### 6.1 1차 안내(시스템 안)
- **[확정]** 변경이 생기면 시스템 안에서 로그인 시 확인할 사항을 안내한다(부록 A-9). 로그인 시 계정별 할 일 목록을 제공한다(부록 A-3).
- **[제안]** 안내 대상: 회의록 공개 시 확인 대상자 전원, 정정 시 바뀐 항목의 당사자(지시자·실무 담당자·관리자). 정정 안내 범위는 아래 6.4의 제안 선택지.

### 6.2 보조 안내(메일)
- **[확정]** 미확인자에게 하루 1회. 내용은 건명 목록과 로그인 페이지 링크 하나(건별 링크 없음). 로그인해도 안내를 멈추지 않고, 확인 완료·관리자 종결·삭제될 때까지 DB에 남은 건을 계속 안내한다(부록 A-10).
- **[확정]** 메일 시스템으로 확인·결정사항을 안내하고 있음으로 본다. 더 강한 수단은 고객 요청 시 설정 또는 개발로 처리한다(부록 A-11).
- **[확정]** 초기 채널은 시스템 로그인 안내 + 이메일. 문자·카톡은 나중 연동. 건명 노출 제한 옵션은 초기 범위 제외(부록 A-12).

### 6.3 메일 대상 선정 기준
**[제안]** 하루 1회 배치에서 수신자별로 다음을 모은다.

```
for 계정 in 고객사의 활성 계정:
    건명 목록 = [항목 for 항목 in 항목들
                 if 계정 이 항목의 확인 대상자          # 참석자·비참석 실무 책임자·관리자
                 and 회의록.상태 != draft               # 공개 전 초안은 메일 대상 아님 [제안]
                 and 항목.확정 상태 == pending]           # confirmed(모든 kind)·closed·deleted 는 전원 제외 [확정]
    if 건명 목록: mail_digest_built 기록 → 발송 → mail_sent / mail_failed 기록

항목이 confirmed 가 될 때(사람 확인·자동 확정 모두):
    다음 일일 메일부터 모든 대상자의 건명 목록에서 빠짐(위 조건)
    담당 관리자에게 notice_raised(구분 item_confirmed_to_manager) 1회      # [확정] 1회 시스템 안내
                                                                       # [제안] 표시는 관리자 로그인 시 화면, 메일은 보내지 않음(사용자 확인 대기)
```

- **[확정]** 로그인 여부는 대상 선정에 쓰지 않는다(로그인해도 안내를 멈추지 않음, 부록 A-10).
- **[확정]** 항목이 confirmed가 되면(사람 확인·자동 확정 모두) 모든 대상자의 일일 메일 목록에서 즉시 제외한다(출처: 팀장 회신 2026-10-01, 8절 A·C).
- **[제안]** 발송 단위는 수신 계정별 하루 1통, 건명에 넣을지는 항목 단위(항목 확정 상태)로 판정한다. 계정별 확인 여부로 판정하지 않는다.
- **[확정]** 담당 관리자에게는 확정 사실을 1회, 시스템으로 안내한다(출처: 팀장 회신 2026-10-01, 부록 B-1).
- **[제안]** 위 관리자 안내는 관리자 로그인 시 화면에 표시하고, 메일은 보내지 않는다(출처: 위 회신에서 구체화한 설계 제안이며 원문에는 없음, 사용자 확인 대기).
- 참고: 선택되지 않은 안(계정 단위, 각 대상자가 본인 확인할 때까지 메일 계속)은 8절 C 표에만 남긴다.
- **[제안]** 같은 날 두 번 발송되지 않도록 (고객사, 수신 계정, 날짜)로 한 번만 발송(멱등).

## 8) 결정 A·B·C·D와 미결 E의 영향 범위

A·B·C·D는 팀장 회신 2026-10-01로 [확정]됐다(부록 B). 각 표에서 선택된 안의 열 머리에 "✔ 선택"을 붙이고, 선택되지 않은 안은 참고용으로 남긴다.

### A. 자동 확정된 건을 메일 대상에서 제외할지
- **[확정]** 제외. 항목이 confirmed가 되면(자동 확정 포함) 모든 대상자의 일일 메일 목록에서 즉시 제외한다(출처: 팀장 회신 2026-10-01, A+C).
- C와의 관계: C가 항목 단위(C-1)로 정해졌으므로 사람 확정·자동 확정 모두 같은 규칙(전원 제외)을 따른다.

| 영향 받는 곳 | 제외할 때 ✔ 선택 | 포함할 때(참고) |
|---|---|---|
| 메일 대상 선정(6.3) | `confirm_kind in (period_elapsed, due_reached)`인 항목은 건명 목록에서 뺌 | 계정이 확인할 때까지 계속 포함 |
| 부록 A-10과의 관계 | "확인 완료·관리자 종결·삭제될 때까지"에 "자동 확정"을 중단 사유로 추가하는 해석이 필요 → 정책 문구 보완 필요 | 부록 A-10 문구 그대로 |
| 메일 길이·피로도 | 오래된 건이 빠져 목록이 짧게 유지 | 확인 안 하는 사람의 목록이 계속 길어짐 |
| "확인 없이 확정" 추적 | 메일 대신 화면(관리자 점검 목록, 아래 A-10 해석 메모)에서 따로 보여 줘야 함 | 메일이 계속 확인을 유도 |
| 사건 원장 | `mail_digest_built`에 제외 사유 기록 필요 | 변화 없음 |
| 법무 | 자동 확정 효력 판단과 연결([법무 검토 필요]) | 동일 |
| 데이터 이전 | 없음(선정 로직만) | 없음 |

- **[제안] 부록 A-10 해석 메모:** 부록 A-10 원문은 확인 완료·관리자 종결·삭제까지 안내라고만 되어 있다. 자동 확정(`period_elapsed`, `due_reached`)을 메일 중단 사유로 읽는 것은 해석이며, 근거는 팀장 회신 2026-10-01(A+C)이다.
- **[제안] 설계 메모(사용자 확인 대기):** 자동 확정된 항목은 담당자가 직접 확인하지 않았으므로, 메일은 중단하되 로그인 시 해당 계정의 할 일 목록에 "자동 확정됨(미열람)"으로 표시하고, 담당 관리자 안내(`notice_raised`, 구분 `item_confirmed_to_manager`)에 `confirm_kind`를 포함한다.

### B. 5일/10일을 고객사 단위로만 둘지, 회의 단위도 허용할지
- **[확정]** 초기에는 고객사 단위 설정(기본 5일, 촉박 시 10일)만 지원한다. 회의 단위 확장은 `policy_snapshot` 확장 자리(4.2, `source` 필드)로만 열어 두고 구현하지 않는다(출처: 팀장 회신 2026-10-01).

| 영향 받는 곳 | 고객사 단위만 ✔ 선택 | 회의 단위도 허용(참고, 나중 확장) |
|---|---|---|
| 정책 저장 | `policy(tenant_id, auto_confirm_days)` | 회의(또는 회의록)에 `auto_confirm_days` 덮어쓰기 값 추가 |
| 계산(5.2) | N = 고객사 값 | N = 회의 값 ?? 고객사 값 |
| 화면 | 운영 설정 화면만 | 회의록 작성 화면에 선택 항목 추가, 누가 바꿀 수 있는지 권한 필요 |
| 사건 원장 | `policy_snapshot`에 고객사 값 | `policy_snapshot`에 출처(고객사/회의) 함께 기록 |
| 회의록 생성 후 변경 | 고객사 값 변경이 이미 생성된 회의록에 적용되는지 결정 필요 | 회의 단위 값을 회의록 생성 후 바꿀 수 있는지 결정 필요(기산점은 최초 생성 시각 고정·리셋 금지([확정])와 충돌 가능) |
| **데이터 이전** | 나중에 회의 단위를 허용해도, 과거 회의록이 어떤 N으로 계산됐는지 알 수 있어야 함 → **[확장 자리]** 회의록에 "적용된 N" 열(또는 `minutes_created` 사건의 `policy_snapshot`)을 처음부터 기록 | 동일 |

### C. 한 사람이 확정하면 다른 대상자의 메일도 멈추는가, 계정별로 따로 도는가
- **[확정]** C-1 항목 단위. 항목이 confirmed가 되면(자동 확정 포함) 모든 대상자의 일일 메일 목록에서 즉시 제외하고, 담당 관리자에게는 확정 사실을 1회, 시스템으로 안내한다(출처: 팀장 회신 2026-10-01, 부록 B-1, 6.3).
- **[제안]** 위 관리자 안내는 관리자 로그인 시 화면에 표시하고, 메일은 보내지 않는다(출처: 위 회신에서 구체화한 설계 제안이며 원문에는 없음, 사용자 확인 대기).
- 참고: C-2 계정 단위(각 대상자가 본인이 확인할 때까지 메일 계속)는 선택되지 않았다.

| 영향 받는 곳 | C-1 항목 단위(전원 종료) ✔ 선택 | C-2 계정 단위(각자 확인까지, 참고) |
|---|---|---|
| 메일 대상 선정(6.3) | 항목 확정 상태만 보면 됨 | 계정별 확인 사건(`item_confirmed`/`item_acknowledged`)을 항목마다 조회 |
| 부록 A-6과의 관계 | "누구든 확인하면 확정"과 자연스럽게 맞음 | 확정 뒤에도 안내가 계속돼 "확정됐는데 왜 또 오나" 혼선 가능 |
| 부록 A-10과의 관계 | "확인 완료"를 항목의 확정으로 읽는 해석 | "확인 완료"를 각 대상자의 확인으로 읽는 해석 |
| 다른 대상자가 내용을 모르고 지나갈 위험 | 있음 → 담당 관리자에게 확정 사실 1회 시스템 안내로 보완([확정]). 전달 방식은 [제안](로그인 시 화면, 메일 없음) | 낮음(각자 확인할 때까지 안내) |
| 메일 길이·피로도 | 짧음 | 길어짐(이미 확정된 건도 남음) |
| 사건 원장 | 관리자 안내를 `notice_raised`(구분 `item_confirmed_to_manager`)로 기록. 메일 사건은 없음([제안] 전달 방식에 따름) | 변화 없음(대상자별 확인 기록이 이미 있음) |
| A와의 관계 | 사람 확정·자동 확정 모두 같은 규칙(전원 제외) | A는 계정별 미확인 건 전체에 걸림 |
| 데이터 이전 | 없음 — 단, 나중에 C-2로 바꿀 수 있으려면 확정 뒤 다른 대상자의 확인도 계속 기록해야 함(3.4 `item_acknowledged`, 이미 제안에 포함) | 없음 |

### E. 운영 백엔드 세부 선택
- **[미결] E1~E4** D 방향에 따라 생긴 질문이다. 각 표는 선택지와 영향만 적고 결론은 내리지 않는다.

#### E1. DB 엔진과 ORM 선택
- **[미결] E1** 현재 구조(v1)는 SQLite 파일 + 표준 `sqlite3` 직접 SQL이며 ORM이 없다(`backend-contract-stub/app/db.py`). Alembic은 SQLAlchemy 위에서 동작하므로, Alembic을 쓰려면 SQLAlchemy(Core 또는 ORM)를 함께 도입해야 한다.

| 영향 받는 곳 | SQLite 유지 | 서버형 DB(예: PostgreSQL) |
|---|---|---|
| 동시 접속·배치 | 쓰기 잠금이 파일 단위라 동시 쓰기에 약함 | 동시 쓰기·배치 작업에 유리 |
| Alembic 사용 | 가능. 단 SQLite는 열 변경 제약이 있어 표 재생성(batch 모드) 필요 | 제약 적음 |
| 추가 전용 보호(4.1) | 트리거로만 가능, 계정 권한 분리 없음 | 계정 권한·트리거 모두 가능 |
| 운영 부담 | 파일 하나, 백업 쉬움 | DB 서버 설치·운영 필요 |
| v1 데이터 이전(E4) | 같은 엔진이라 변환이 적음 | 엔진 간 변환 필요 |
| 새 의존성 | SQLAlchemy·Alembic | SQLAlchemy·Alembic·DB 드라이버 |

#### E2. 저장소 밖 기존 `backend/`(테스트 76건)
- **[미결] E2** 그 코드는 이 저장소에 없고, 이번에 열어 보지 않았다(8절 D 사실 표). 판단 전에 코드 확인이 먼저 필요하다.

| 영향 받는 곳 | 재사용 | 신규 작성 |
|---|---|---|
| 착수 속도 | 쓸 수 있는 부분이 많으면 빠름 | 처음부터 작성 |
| 현재 계약(`docs/API-CONTRACT.md`)과의 정합 | 구 코드가 현재 계약과 맞는지 대조 필요(확인 못 함) | 계약 기준으로 작성 |
| 원장·상태 모델(3~5절) | 구 구조에 맞춰 넣거나 고쳐야 함 | 이 문서 기준으로 설계 |
| 테스트 76건 | 남은 테스트가 안전망이 됨(유효성 확인 필요) | 새로 작성. 스텁 133건을 기준으로 옮길 수 있음 |

#### E3. 스텁(`backend-contract-stub/`)의 이후 역할
- **[미결] E3**

| 선택지 | 영향 |
|---|---|
